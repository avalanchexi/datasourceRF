# 数据质量体检

对**一次已完成的运行**及其 120 日证据窗口做只读体检，回答三个问题：数据取全了吗？进模型的输入全吗？模型输出对吗？结果输出为 Markdown 报告，只报告问题，不阻断运行，也不改库。规格见 `.scratch/data-quality-audit-20261010/spec.md`。

目前已实现第一层中的日频逐日核对、低频的最新期与发布延迟核对（票 01），以及派生数据的存在性与独立重算（票 02，商品篮子分项广度由模型规则补全批次票 04 补上）；第二层模型输入完整，以及第三层的输出内部一致性复查（票 03，库存象限三条线由模型规则补全批次票 05 补上）和三核心独立重算（票 04）。

## 用法

```bash
python tools/quality/audit.py --run <run_id> [--database <path>] [--out <md>]
```

- `--database` 默认为 `~/.local/share/pring-cycle/pring-cycle.sqlite3`，以 `file:...?mode=ro` 只读方式打开；制品原件从同级的 `artifacts/sha256/<前两位>/<哈希>` 只读读取。
- 不加 `--out` 时报告打印到标准输出。报告末尾会记录本次耗时，对 `run-a8675946…` 实测为 5～9 秒。
- 排序用的临时数据放在内存里（`PRAGMA temp_store = MEMORY`），只读沙箱里也能运行。
- 被审运行必须处于 `completed` 状态。截止时点取 `run_cutoff_freeze.system_as_of`；若该表无记录，则退回 `parent_run.system_as_of`。所有“已持有”都以 `available_at <= 截止` 为准，所以审旧运行时，运行之后才入库的数据不会被算进去。
- 公共读取中的取数回执（`Run.receipts`、`reached_source`、`validated_by_cutoff`）和日历回执的合并顺序，都先把时间解析成带时区的时刻，再与截止比较或排序，不按文本比较（体检票 07，`.scratch/model-rules-followups-20261012/issues/07-audit-script-residuals.md`）。这样，`Z` 与 `+00:00`、空格与 `T`、不同时区的写法都按实际时刻判断。解析用标准库 `datetime.fromisoformat`（先把 `Z` 换成 `+00:00`），能解析的范围以本机 Python 为准；例如 Python 3.10 只认 3 位或 6 位小数秒，`.5` 这种写法会记为解析不了。时间为空、缺时区或解析不了时记为不可用，不猜时区：发起时间不可用的回执不算截止前发起，应答或校验时间不可用的回执不算截止前取得应答或通过校验。截止本身解析不了或缺时区时，体检直接报错退出。
- 各层模块中直接写在 SQL 里的截止比较（如 `available_at <= 截止`、部分回执查询的 `started_at`、`received_at`、`validated_at`）仍按文本比较；公共读取之外，还有一处在 Python 中按文本比较，即第一层读发布公告回执时，`validated_at` 与截止的比较（`acquisition.py` 的 `_load_announced`）。这些都不在票 07 范围内。库中时间都是统一的 UTC 写法（带 `+00:00`）时，文本与时刻比较结果相同；`run-b7d59b63…` 的快照即如此。
- `full_run_acquisition` 中 `phase='referenced'` 的行（票 30 引入）是本运行引用的旧回执，不是它自己发出的请求。读原件时，这些回执算作本运行可见（日历、核心原件）；统计本运行的请求和回执时则排除（`acquisition.py` 中声明过该指标的回执、`model_input.py` 的回执状态统计、`core_recompute.py` 中早前运行自己的核心回执）。
- 从源码目录直接跑时，建议加上 `PYTHONDONTWRITEBYTECODE=1`，避免在 `tools/quality/` 下留下字节码。

## 独立性约束

- 只用 Python 标准库，**不导入 `pring_cycle`**，也不照抄生产代码里的计算逻辑。规则来源只有三类：库里存储的数据、冻结模型清单（`model_version.manifest_json`），以及本文档写明的内置表。
- 脚本不做任何外部调用，不启动 Worker，也不写库。
- 唯一抄录自生产代码的是来源声明的编号规则（见“三核心窗口前冻结编号的精确恢复”）：它是存储格式，不是被核对的计算；按用户 2026-10-11 的决定写入本文档，脚本只依据本文档实现，并逐份回执用现存声明自检。

## 口径

### 两种范围

每项结论都分两种口径报告：

- **目录全部指标**：冻结模型目录（`metric_definitions`）中的全部指标。
- **仅模型用到的指标**：`core_metrics` 中的核心指标、`confirmation_rules` 里任意位置出现过的目录指标编号，再加上 `warrant_conversions` 指向的 `CN_FUTURES_WARRANTS`。v0015 下共 47 项。

以下几类只计入“目录全部”：国际参考类 P2 指标（VIX、SOX、UST2Y／10Y、人民币中间价、16:30 收盘价、ECB 交叉汇率）、运维类指标、确认规则没有引用的派生项。

不进入本层逐格核对的指标：

- 运维类：`CN_TRADE_CALENDAR`、`CN_RELEASE_SCHEDULE`、`SOURCE_OBSERVED_AVAILABILITY`。日历本身的覆盖范围在“日历与窗口”一节单独列出。
- 只有派生值、没有来源声明的指标（`derived_only`），归第一层第三条（票 02）处理。
- 事件型指标，例如 `CN_RRR_EVENT`：没有固定期次，只列名。

### 窗口

窗口取上交所日历中截至目标日的最后 N 个开市日，N 来自冻结清单的 `visible_evidence_window_trading_days`（当前为 120）。报告会把它与最终计划里的 `daily_window` 比对，并给出一致或不一致的结论。

非上交所市场使用同一段自然日区间（窗口首日到目标日），再按各自市场的日历筛选开市日。

### 日频：逐交易日 × 成员

在窗口区间内，对每个日频指标的每个成员、该市场每个开市日记一格，每格归入以下四类之一：

| 类别 | 判据 |
|---|---|
| 已持有 | 截止前已入库的该指标、该成员、该日的 `source_claim`。旧目录版本的声明，只要该指标在那个版本中的定义与冻结定义相同（只允许 `definition_version`、`priority`、`certification_status`、`name_cn` 不同，见 `common.IDENTITY_NEUTRAL`），也算已持有，并在“其中仅旧目录版本”一列单独计数。只有定义不同的旧版本声明的格不算已持有，并在依据里注明 |
| 上游未发布 | 证据来自最近一条覆盖该日、并在截止前取得来源应答的回执（有原件，且 `received_at` 不晚于截止）。满足以下任一条即判为上游未发布：① 原件是 TuShare 结构（`data.fields/items`），而该日的行数为 0，权证按 `symbol` 分开数；② 该日有行，但成员所需的行键或原件缺了一部分（见下文“成员所需的行与原件”），依据注明缺哪个交易所、指数或原件。①②都要求原件行数没有达到请求的 `limit`：达到时可能分页不全，缺行不作证据，改记未取到；③ 该回执只取这一天，截止前已校验通过，且 `source_record_count = 0` |
| 未取到 | 没有声明，也不满足上面的证据：没有覆盖该日的回执；覆盖该日的回执在截止前都没取得应答（例如被负缓存拦截）；原件里该日其实有成员所需的行（所需值为空的也算这一类：空值、原件损坏（任一行长度与字段数不符或日期无效时，整份原件不作逐日证据；缺行键列、行键为空或不是字符串；权证原件该日有行却缺 `symbol` 列）、分页不全都不能说明上游未发布）；或者原件不是 TuShare 结构，无法逐日核对。报告会附上所依据回执的编号与状态 |
| 日历未覆盖 | 该市场的日历不覆盖这一天，不算缺口 |

**哪些回执算数**：截止前发起的回执中，只看“请求的是这个成员的序列”的那些。具体做法是：先找出截止前为该成员在窗口内产出过声明的回执，取它们的请求签名，即接口名加上除日期类参数以外的全部参数（例如权证的 `symbol`、指数的 `ts_code`）；签名相同的回执都算数。从未持有过的成员，退而使用在运行中声明过该指标的回执（`full_run_acquisition.metric_ids_json`）；权证还要求回执请求的正是该品种（参数 `symbol`）。覆盖区间从参数中的 `start_date`／`end_date`／`trade_date`／`period`／`date` 推出。比最近一条取得应答的回执更新、但没有取得应答的尝试，不作为证据，只在依据里计数。

下面的事件类指标不用这套签名规则：公告逐页请求，签名里带着各页的 `source_url`，同一指标其他日子的公告会被漏认（票 09 的根因）。

**成员所需的行与原件（票 13）**：“该日有行”还不等于成员要的数据齐了。合计类和多原件的成员，按成员自己需要的行键、字段或原件核对。规则是内置表，只依据成员维度的含义和原件字段名，不导入生产解析器：

| 内置表 | 指标 | 成员需要什么 | 部分缺项 |
|---|---|---|---|
| `MEMBER_ROWS` | `CN_MARGIN_BALANCE_SSE_SZSE` | `scope` 所含交易所各一行（`exchange_id`；`sse_szse` 为 SSE、SZSE，旧三所口径 `all_exchanges`／`SSE+SZSE+BSE` 另含 BSE），字段按 `measure` 取 `rzye`／`rzmre` | 缺某交易所的行：上游未发布，依据写“应答该日缺 SZSE”等 |
| `MEMBER_ROWS` | `CN_SHIBOR_ON_1W_3M` | 当日一行，字段按 `tenor` 取 `on`／`1w`／`3m` | 该期限为空：未取到（空值不算上游未发布） |
| `MEMBER_ROWS` | `CN_INDEX_VALUATION` | 该指数（`ts_code` = `index`）一行，字段按 `measure` 取 `pe`／`pb`／`turnover_rate` | 缺该指数的行：上游未发布；字段为空：未取到 |
| `MULTI_RAW`（全都需要） | 股市广度七项（涨跌家数、涨跌比、上涨成交额占比、90／250 日新高新低、90／250 日均线上方占比） | 该成员的回执里出现过的每个按日原件序列（接口名加非日期、非分页参数为一个序列，同一序列的各页算一个；交易日历、不带日期的股票列表除外；目前是 `daily` 和 `stk_factor_pro`）。每个序列都必须有覆盖该日的首页（`offset` 为 0 或不带），取截止前取得应答的最新一份；首页没有截断时，它含该请求的全部行 | 某个序列该日 0 行、其余有行：上游未发布，依据写缺哪个原件；全部 0 行：上游未发布 |
| `MULTI_RAW`（不推断） | 商品篮子 `CN_COMMODITY_EX_HOG_BASKET`、分袖贡献 `CN_COMMODITY_SLEEVE_CONTRIBUTION` | 同上，按合约（`ts_code`）分序列，但只看覆盖该日的合约 | 所需合约随换月而变，脚本不推断：只有覆盖该日的合约全部 0 行才判上游未发布，部分 0 行仍记未取到 |

多原件成员中，必需的序列没有覆盖该日的首页、首页在截止前都没取得应答、原件不是 TuShare 结构，或首页行数达到请求的 `limit`（分页可能不全）而该日 0 行，都记未取到，并在依据里列明。多原件成员只读行数（不缓存整行），以免广度原件（每份约 5500 行）占用内存。其余指标照旧按“最近一份原件该日有无行”判断。

局限：
- 权证只按品种分成员，不核对仓库和数值字段。
- 规则表之外的合计类指标，仍按该日行数判断；新增此类指标时要补表。规则表遇到不认识的成员维度（例如未知的 `scope`）时，也退回按行数判断。
- 单原件路径仍取覆盖该日的最新一份应答，不区分分页；目前带分页参数的只有广度，已归多原件处理。
- 应答缺某交易所，只说明当时 TuShare 的应答里没有它，不能单独证明交易所官网尚未发布。

**成员**：

- 权证按品种（`symbol`）划分成员，品种取窗口内出现过的品种与 `warrant_conversions` 列出品种的并集。每个品种使用其 `exchange` 维度对应交易所的日历。
- 其他指标以窗口内出现过的每一组完整维度为一个成员。没有任何声明的指标记为一个成员：无维度的记作“—”，有维度的记作“（无任何声明）”。
- 局限：从未出现过的成员发现不了。

**公开时间晚于目标日**：有些格已经持有，但声明的公开时间（取 `public_available_at`，缺失时取 `inferred_public_at`）晚于目标日结束。这些格单独列表：它们取数是完整的，只是按时点规则不进模型，由第二层报告。

### 日频：事件类与按需求口径的指标（票 09）

有两类日频指标不按“每个交易日都应有观测”核对。它们不计入应有格的日子另记一类，不算缺口；报告的日频总表只计各自口径下的应有格，结论里另起一条说明，“日频：按事件与需求口径核对的指标”一节列出口径、不计入的日期，以及待重处理的公告回执。

**事件类（现行值）**：冻结清单 `confirmation_rules` 中带 `notices` 的规则所读的指标。v0015 只有 `CN_OMO_7D_RATE`，`notices` 指向 `CN_OMO_7D_AMOUNT`（`measure=injection`）。这类指标只在公告给出新值的日子有观测，其余日子沿用此前公告的现行值。有声明的日子照常记“已持有”；没有声明的日子按当日公告判断：

- **当日公告**：参数 `family` 等于该指标目录 `release_event_family`（这里是 `pbc_omo_notice`），`period` 等于该日，截止前取得应答的回执，按发起时间由新到旧排列。只读截止前已通过校验的规范化制品（`normalized_hash`，有 `accepted_scalars` 键时取它，否则取 `scalars`，或顶层数组；空列表算一份不含任何值的解析件；由 `Run.scalars` 按哈希读取并缓存），列表页之类没有标量列表的制品不算公告解析件。标量的单位须是字符串、值须是数或字符串，形状不对的不作证据。

| 当日公告的情况 | 类别 |
|---|---|
| 任一解析件含该指标、该成员、该日的值（单位须是冻结定义允许的） | 未取到。依据写明“原件含值、未入库，待重处理（票 09 线 B）”和解析件中的值，并在专表中逐日列出所依据的公告回执，供线 B 重处理 |
| 有解析件，都不含该值，而且每份解析件都给出 `notices` 指标当日的值、都为 0 | 公告无新值：当日无操作，不计入应有格 |
| 有解析件、不含该值，但有一份解析件的 `notices` 值非 0 或缺失 | 未取到：无法确认当日无新值 |
| 当日公告回执都没有可读的解析件；或者没有当日公告回执（依据里注明当日是否有 `notices` 指标的声明） | 未取到 |

“`notices` 值为 0 即无新值”是本脚本的取舍：公开市场公告在操作量为零的日子不列利率。报告另列窗口前最近一条已持有声明的日期和值（窗口开始时的现行值），只作说明，不计格。

**只要最新值的指标**（内置表 `acquisition.LATEST_ONLY`）：三项 P2 参考指标，都只要最新值和比较上下文，不补 120 日历史：

| 指标 | 依据 |
|---|---|
| `CN_USDCNY_CENTRAL_PARITY` 人民币中间价 | 用户 2026-10-10 决定（票 09） |
| `CN_USDCNY_CLOSE_1630` USDCNY 16:30 收盘价 | 用户 2026-10-11 决定，同人民币中间价（残余分流票 04） |
| `NASDAQ_SOX_INDEX` SOX | 同上 |

依据是生产的用法：这几项不参与正式阶段与确认度，国际背景只取每个成员的最新值和前一个值算方向（`context_projection.py`）。

- **应有格**只有两个：窗口内该市场最后一个不确知休市的日子（最新值），以及它之前最近一个已持有的日子（比较上下文；窗口内没有时取再前一个不确知休市的日子）。日历未覆盖的日子照常记“日历未覆盖”。
- **其余日子**记“不在需求内”，不计入应有格，已持有的也一样，另列“其中已持有”。没有持有的日子仍照常分类（未取到、上游未发布等），按类别列在“需求外缺格”一栏。这只是信息，不计入“未取到”。
- **第二层不变**，仍核最终计划要求的期次。计划要求的某一期在第一层落在需求外时，第二层“第一层”一栏写“不在需求内（原类别）”，原因沿用原类别的依据（见“缺失明细”）。
- **SOX 的授权缺口**：ADR-0029 规定 SOX 按受限授权 P2 处理，透明缺口，不检索，所以没有取数路径，两个应有格照记“未取到”。脚本的内置表 `acquisition.NO_PATH` 列出这类指标，结论和“按事件与需求口径核对的指标”一节都会注明这一缺口，不会因为应有格变少而消失。

### 月频、季频、周频：最新应有期与发布延迟

**发布依据**，按以下顺序确定：

| 指标 | 依据 |
|---|---|
| 国家统计局各项 | 运行批次 `release_schedule` 中 `nbs:schedule_page` 的条目，对应关系见 `acquisition.NBS_SCHEDULE`。PMI 在当月发布当月数据，其余指标发布上一个月或上一季度的数据；季度条目只取 1、4、7、10 月的发布 |
| LPR | 冻结规则 `monthly_day_20_holiday_roll_0900_asia_shanghai`：每月 20 日 09:00 发布，遇上交所休市日顺延 |
| 其他（人民银行货币信贷、央行工具月度投放等） | 没有官方日程，只能以截止前已入库声明的公开可用时间推定。**局限**：如果整期都没取到，这里发现不了。报告的“发布依据”栏会写明这一点 |

周频按 ISO 周编号期次（v0015 目录中没有周频指标）。

低频只计与冻结定义相同的目录版本的声明（同日频的 `same_definition` 口径）。

**最新应有期**：截止前已经发布的最近一期（按上表依据判断）。截止前该期有任何声明入库，判为“在”，否则判为“缺”。备注栏列出上一期有、本期却缺的成员数。

**超过宽限**：只看发布时间落在窗口首日到截止之间的期次。宽限截止是发布日之后第一个国内开市日的 23:59:59（北京时间）。上交所日历覆盖不到时，改用 SHFE 期货日历判断开休市（内地交易所节假日相同），并在“依据”栏注明；两者都覆盖不到时，记为“宽限无法判定”，在结论中单独计数，不算超过宽限。以下两种情况列为超过宽限：首次入库时间（最早的 `available_at`）晚于宽限截止；或者到冻结截止仍未入库，且截止已晚于宽限截止。到冻结截止时仍在宽限内的期次不列。

发布时间早于系统启用时间（库内第一条回执的时间）的期次，是系统启用后回填入库的。这些期次照样列出并计数，只在“启用前发布”栏标“是”，结论中另外给出数量。

**现已无声明的期次（票 10）**：发布落在窗口首日到截止之间、但库里已没有该期任何声明的期次，不能直接当作“到截止未入库”。留存会删掉窗口外、没有投影引用的声明（`retention.py` 的 `retired_claim`），被删的期次下一轮可能再取、再删。脚本只读本运行最终计划（`full_run_gap_plan` 的 `final`，冻结于截止）和截止前的回执，0 次外部调用，按下列顺序分三类，列在超宽限表之后的明细表里（“已入库后被清理”逐成员列出，见下文），并附依据：

| 类别 | 判据 | 超宽限表中的处理 |
|---|---|---|
| 已入库后被清理 | 满足任一条：① 最终计划 `requirements` 中该指标、该期选中的 `selected_claim_ids` 现已全部不在 `source_claim`；② 某次运行在 `full_run_acquisition` 中为该指标声明过的回执，截止前已校验（`validated`）且 `ingest_result = 'accepted'`，其规范化制品（`Run.scalars`，优先 `accepted_scalars`）含该指标、该期（按 `period_end` 定期次，不含日频）的值 | 有②时，首次入库取这些回执中最早的 `validated_at`，照常判宽限，“首次入库”栏注明已被清理；只有①时入库时间不明，不进超宽限表，只列在明细表 |
| 不在需求内 | 不满足上一条，且最终计划对该指标有需求行、却没有这一期（例如核心 CPI 是辅助成员，只回看 3 期） | 不是应有期，不进超宽限表，也不算超过宽限 |
| 未取到 | 其余情况：计划要求该期却没入库，或计划里没有该指标的需求行、无法判定需求 | 照旧记“到截止未入库，已超宽限”（仍在宽限内的不进超宽限表） |

结论中“到截止仍未入库”只计第三类；“已入库后被清理”和“不在需求内”另外计数。

**清理明细按成员列出（模型规则后续批次票 05）**：一个期次只要还有任一成员的声明，就不算“现已无声明的期次”，但其他成员可能已被清理（例如工业财务某期的营收同比已清理而利润同比仍在）。所以明细表中的“已入库后被清理”逐成员列出，一行是一个“指标 × 期次 × 成员”：

- **成员**是指标的一组维度，按键排序后的 JSON 比较，无维度记“—”。声明取 `dimensions_json`，回执标量取 `dimensions`，计划取需求行 `members` 中去掉“指标:”前缀的部分。
- **范围**同上：发布落在窗口首日到截止之间的期次，不论该期是否还有其他成员的声明。
- **判据**：该成员该期没有截止前入库的同定义声明（与“最新应有期”同口径），且满足任一条：① 最终计划该期的需求行在 `members` 中列有该成员（不在 `missing_members` 中），且该行的 `selected_claim_ids` 至少有一条现已不在 `source_claim`；② 上表②所说的回执中，有一条的已接受标量含该指标、该期、该成员（维度相同）的值。依据栏分别写出该成员的计划证据与回执证据（回执条数、运行次数、最早与最近一条）。
- 整期无声明、按上表判为“已入库后被清理”，却认不出任何成员时（只有①且计划没有列出成员），记一行“成员不明”，依据沿用期次的依据。
- 明细表前另列“成员数／指标期次数”，并注明其中几期仍有其他成员的声明；结论中也另列这两个数。“不在需求内”“未取到”仍逐期一行，成员栏记“整期”。

不变的部分：期次的三类划分、结论中“现已无声明的期次”的计数、最新应有期、超宽限表与“首次入库”都仍按指标期次计。仍有其他成员声明的期次照旧按现存声明判宽限，不因部分成员被清理而进超宽限表。这里只列被清理的成员；从未入库的成员不列（上一期有、本期缺的成员数见“最新应有期”的备注）。

局限：
- 退役运行的回执已随留存删除，所以“最早”只是现存回执里最早的一条，真实首次入库可能更早。
- 只看声明过该指标的回执；被别的指标的回执顺带入库、又被清理的期次或成员，只能靠计划认出。
- 回执的标量不带目录版本，不检查定义是否与冻结定义相同。
- 曾被清理、后来又重取入库（截止前）的成员不列为被清理；期次的“首次入库”仍按现存声明计。

### 派生数据：存在性与独立重算（票 02）

实现在 `tools/quality/derived.py`。被审运行用到的派生值分四类存放，都要核：

- **派生观测表** `derived_observation`：运行为目标日落库的派生值（`batch_id` 等于运行编号）。每个公式一行，贷款按成员各一行，只存最新齐全期。
- **窗口内各日的汇总投影**：每个交易日发布一份投影。目标日取被审运行自己的投影，其他日子取数据截止（`system_as_of`）不晚于被审运行截止的最新一份；没有投影的交易日列为问题。补算日的派生值只写进当日投影，不落派生观测表（`persist_derived=False`，见 `.scratch/architecture-review-20260929/issues/12-backfill-day-evidence-snapshot.md`），所以“窗口内每一天”要在各日投影里核。这一处只核冻结清单 `derived_formula_versions` 中的公式。
- **本运行发布的投影**（`Run.datasets` 的 `macro`）：确认规则里规则级公式按期给出的序列，包括 M1−M2、DR007 每期政策利差、当月增量较去年同月、每期净投放，以及价格一致性中的相对动量。

- **股市广度**：系统按 ADR-0030 逐股计算、再以来源声明入库的 7 项序列。本节按窗口内每一天，从 TuShare `daily` 与 `stk_factor_pro` 原件重算，再与截止前可用的声明比对。

逐项结论表列出 v0015 的全部派生指标，共 22 项：冻结清单 `derived_formula_versions` 中的 8 个公式、确认规则中的 7 个规则级公式，以及 7 项股市广度。商品篮子与分项贡献以来源声明入库，归在规则级公式 `ex-hog-calendar-settlement-v0003` 一项里，这一项核的是本运行投影中的商品篮子分项广度（见下文“商品篮子分项广度”）。

**原料**：只用当时能用的来源声明。“当时”对目标日指截止时点，对窗口内其他日子指该日投影的 `system_as_of`。条件有四：当时已入库；公开时间（`public_available_at`，缺失时用 `inferred_public_at`）不晚于该日结束（北京时间）；目录版本与冻结定义相同（`same_definition`，按被审运行的冻结目录判断）；没有被另一条满足前述条件的声明取代（`supersedes_claim_id`）。同一观测有多个来源且取值不一致时，取哪个来源属于选源规则，本节不核：一律用系统所选的那条声明重算，即使它的值为空。派生观测取其血缘，投影读数取 `observation_version_ids`。候选值列在备注里，但生产读取时已排除的资讯声明不列入，见下文“多源备注与资讯声明的读取排除”。

**存在性**：

| 存放处 | 判据 |
|---|---|
| 派生观测（目标日落库、窗口内各日投影） | 从锚定指标的期次由新往旧逐期试算，第一个原料齐全的期次就是“原料最新齐全期”。拿它与库中该公式（贷款按成员）那一条的期次比较：相同为“存在”；库中没有为“缺失”；库中期次更旧为“期次落后”；库中期次更新为“库中期次晚于独立判断”；原料不齐、库中也没有，为“原料不齐，无派生值”，不算问题。库中期次取血缘中锚定指标的最大期次。有两个公式只试锚定指标当时可见的最新一期，不往前回退到更旧的齐全期：实际库存近似（v0002）按定义只锚定最新库存月；贷款年内差分（`loan-ytd-monthly-change-v0002`）每个成员只看最新一期，它与上一期须是同年连续月份（1 月直接取累计值），上一期缺失就不出值（`.scratch/pring-data-acquisition-repair/research-13.md:178`“同年连续YTD”，与生产行为一致，模型规则后续批次票 04）。差分所需的上一期可以早于窗口，原料不按当日可见窗口截取。若血缘中的声明已被留存删除、无从比较，记为“原料已被留存删除，无法核对”，不算问题。窗口内各日按该日投影所用模型的 `derived_formula_versions` 判断应有哪些公式；本脚本没有实现的旧版本公式只计数；只出现在旧模型日投影中的公式，其问题也列入分流 |
| 投影：每期净投放、DR007 政策利差 | 应有期次取自冻结规则，不取自读数：最后一期止于目标日，往前共 `lookback_periods` 期，每期 `period_sessions` 个交易日（流动性 12×5，DR007 50×5）。不在这些期次上的读数列为问题；应有期次缺失且原料齐全的列为问题；原料不齐的缺期只计数（例如政策利率只从窗口前一日起有公告） |
| 投影：M1−M2 | 应有期次为原料齐全的最新月份往前共 3 个月（辅成员回看 3 期，见 `.scratch/macro-semantics-20261006/issues/04-monthly-official-key-indicators.md:35`），判据同上 |
| 投影：当月增量较去年同月 | 读数只给最新一期，须有值，且与原料最新齐全的月份相同 |
| 投影：相对动量 | 三对都应有读数。按定义，121 个交易日里两个核心每天都要有实际收盘：中间缺日时读数应为空，为空记一致，给出读数则列为问题；原料齐全而读数为空，记为有差异 |
| 股市广度 | 窗口内每一天：原件齐全、能算出值，而截止前没有对应声明的，列为缺失 |
| 投影：缺项 | 冻结规则里有、投影里却没有的读数或输入成员，以及期次与值个数不符的序列，都列为问题，不会从报告里消失 |

**已修复、历史保留**（票 08）：窗口内其他日子的投影，若生成它的运行（`projection_set.batch_id` 对应的 `parent_run.accepted_at`）受理早于 ADR-0036 实施（提交 `6fa8941`，2026-10-02 16:05Z），推断当时系统只读本目录版本下的声明（库中的 `code_version` 是安装哈希，无法对应提交，只能以受理时间推断）。这类投影的存在性问题（缺失、期次落后等），改按该日模型的目录版本严格读取再判断一次；若独立判断与投影相符（“存在”或“原料不齐，无派生值”），就归为“已修复、历史保留”：逐日表照样计数，标“（已修复、历史保留）”，分流中单列，不开票。依据是 ADR-0036 最后一条“已发布历史不重算”。被审运行自己的投影、找不到生成运行或运行受理在 ADR-0036 之后的投影不做此归因；严格读取解释不了的问题，包括严格读取下只能记“原料已被留存删除，无法核对”的，照常报。

**只更正核心的日子**（模型规则后续批次票 03）：核心历史口径变化后，窗口内按旧口径汇总的日子会追加更正版本。若某日原汇总的上下文所引用的声明已超出留存，该日只更正三核心状态与正式阶段，宏观与库存上下文不重算，因而这一天没有派生值。依据是 `GLOSSARY.md` 的“单日汇总”条（2026-10-12 用户决定），见 `.scratch/model-rules-validation-20261011/issues/08-correct-core-only-when-day-context-left-retention.md`。窗口内某日的投影须同时满足以下三条，才认定为只更正核心的日子：

1. 该投影的 P0 评估（`p0_assessment`，按 `projection_set_id` 取）中 `corrects.scope = core_only`；
2. 同一投影的 `macro`、`inventory` 两份数据集都是 `context_status = not_recomputed`；
3. 这两份数据集里都没有派生值，按“窗口内各日的汇总投影”的读法找不到派生节点。

评估或任一上下文文档不是对象（JSON 对象以外的值）时，按未带相应标记处理，同样不豁免。

认定后，该日每个公式（贷款按成员）都计为“未重算（按设计）”：不判存在性，也不重算，不算问题，不进分流。逐日表照常计数，并另起一行列出这些日子（相邻开市日合成一段），以及 `corrects.reason` 与 `not_recomputed_reason` 的取值。不能只看文档没有派生值就豁免：三条只满足一部分的，例如评估标了 `core_only` 而某份上下文没有标未重算，或者标了未重算却仍有派生值，照常判断，并把“只更正核心的标记不一致”连同涉及的日子列为问题。局限：原汇总的投影仍在库中，但本节逐日只核截止前最新的那份，即更正版本，因此不会回头核对原汇总里的派生值。实测（票 03）：`run-b7d59b63bedca39d9d2e` 的 04-13～08-13 共 85 天都认定为只更正核心，8 个公式各 85 天（贷款 9 个成员共 765 格）计为未重算；原先算作缺失的 1241 格、原料不齐的 119 格随之转入这一类，派生节“待开票”由 8 项降为 1 项，只剩贷款 08-14～09-11 的 189 格（归票 04）。票 04 让贷款年内差分只看最新一期后，这 189 格（每格最新可见期 2026-07、缺 2026-06）改判为“原料不齐，无派生值”，派生节“待开票”降为 0 项。

**容差**：|库中值 − 重算值| ≤ 1×10⁻⁶ × max(1, |库中值|)，所有公式统一使用。依据是：公式都是对十进制输入做加减乘除，同一份输入重算时，差异只来自浮点尾差；对两次运行实测，一致的值中相对差最大为 2.2×10⁻¹⁴。容差留出的余量远大于浮点尾差，所以超过容差，就说明公式、配期或选料确实不同。反过来不成立：对数值很大的派生值（例如约 7 万亿元的库存近似，容差约 0.07），输入末位的微小改动可能落在容差之内，本节不保证查出这类改动。

**商品篮子分项广度**（模型规则补全批次票 04）：规则按生产现行做法写成，由用户在 2026-10-11 访谈中认可（`.scratch/model-rules-validation-20261011/interview.md` 的 Q7；取证见同目录 `codex-facts-20261011.md` 第 5 条；篮子复利、分项求和、“不一致”读法的原始取舍见 `.scratch/macro-semantics-20261006/issues/09-price-consistency-and-observation-interfaces.md:52`）。体检只依据下列规则重算，与本运行投影 `macro.price_consistency.basket_breadth` 逐项比对。

- **规则来源**：冻结清单 `confirmation_rules.price_consistency.basket_breadth`，含 `metric_id`（分项贡献指标，v0015 为 `CN_COMMODITY_SLEEVE_CONTRIBUTION`，单位百分点）、`dimensions`（v0015 为 `formula_version = ex-hog-calendar-settlement-v0003`）、`sleeves`（分项清单，v0015 共 7 项）和 `texts`（各读法的文字）。
- **跨度**：与相对动量同一段，即截至目标日（目标日不开市时取之前最近的开市日）的 `relative_momentum.sessions + 1` 个上交所开市日，v0015 为 121 日。上交所日历覆盖不到这么远时，不读，`missing` 为 `["trading_calendar_incomplete"]`。
- **首日作锚**：跨度首日只作起点，它的贡献不计入；累计的是其后的 120 日，即展示窗口的每一天（窗口首日的贡献计入）。
- **原料**：分项贡献的来源声明，维度包含规则 `dimensions` 的全部键值（可以另有其他维度），`sleeve` 在 `sleeves` 中；同一分项、同一天的声明合为一格的候选。候选的条件与本节“原料”相同（截止前入库、目标日结束前公开、目录定义与冻结定义相同、未被取代）。选源不核：一格有多条候选时，以系统所选的那条（出现在本运行投影 `macro` 的冻结输入编号中）为准；没有系统所选时，只有候选取值唯一才用（取值不一致而系统没有选定，即生产的选源冲突，该格不可用）。所用的声明还须 `quality_status = validated`、`value_state = reported_value`、值为数值，否则该格不可用。
- **缺项**：任一分项在累计的某一天没有可用值，整项不读：`status = unconfirmed`，方向、篮子收益、同向数与读法都为空，各分项累计为空。`missing` 按 `sleeves` 的顺序逐个分项列出缺的日子，相邻的开市日合成一段，写作 `分项:日` 或 `分项:起..止`。
- **分项累计**：每个分项把 120 日的贡献直接相加，单位为百分点（`sum_pp`）。方向与 0 比较，容差 1×10⁻¹²：大于 1×10⁻¹² 为 `up`，小于 −1×10⁻¹² 为 `down`，其余为 `flat`。
- **篮子**：不用分项累计相加，而是从 1 起逐日复利：水平 ×=（1 + 当日各分项贡献之和 / 100）。篮子收益 `return_pct` =（水平 − 1）× 100。方向用水平与 1 比较，容差 1×10⁻⁹，规则同上。
- **同向数与读法**：`along` 是方向与篮子方向相同的分项数，`of` 是分项数。读法按顺序判定：篮子 `flat` 为 `flat`（篮子持平）；`along = 0` 为 `unaligned`（逐日涨跌相互抵消，没有分项与篮子同向）；`along × 2 > of` 为 `broad`；`along = 1` 为 `single_sleeve`；其余为 `few_sleeves`。后三者按篮子方向加 `_rise` 或 `_fall`。`text` 取冻结 `texts` 中该读法的文字。能读时 `status = read`。
- **系统计入的输入**：系统把读到的分项贡献声明记入本运行投影 `macro` 的冻结输入编号。能读时，计入的声明应恰好覆盖“分项 × 累计的 120 日”每格一条；跨度首日与跨度之外不应有。

比对方法：分项累计与篮子收益按本节统一容差比较，计入逐值比对；方向、同向数、分项数、读法、文字、状态与 `missing` 要求完全相同，不读时篮子收益与各分项累计须为空，不同的列为问题。投影里的分项按名称对应，不要求与冻结清单同序，但须恰好是冻结的那些分项、各出现一次。原料不齐、系统却给出读数时，记“原料不齐”（多半是声明在运行后被留存删除），不算问题。报告在“商品篮子分项广度”一节逐分项列出两边的累计和方向，以及计入输入的核对结果。

局限：

- 分项方向的容差只有 1×10⁻¹² 个百分点。累计和恰在 0 附近时，求和顺序不同可能让方向翻转。本脚本按日期顺序相加，与库中值的差异落在容差内而方向不同的，照常列为问题，需要人工判断。
- 只核本运行投影中的这一份读数，不核窗口内其他日子投影里的读数。

**无法独立核对**（报告中标为“已知”）：

- `ex-hog-calendar-settlement-v0003` 的商品篮子水平和分项贡献序列本身：篮子要用逐合约结算价，按换月规则从期货原件重建，本脚本没有实现。上面的分项广度以入库的分项贡献声明为原料，不核这些声明本身的取值。

**局限**：

- 相对动量的基日是窗口首日的前一个交易日。被审运行之后只要又有一次运行成功，留存就会删掉这一天的核心价格，相对动量随之只能报“原料不齐”；10-10 的两次运行即属此种情况。所以应在运行结束后尽快体检。
- 补算日的派生值不落库，其血缘声明到了窗口外就会被留存删除。这些日子只能记“原料已被留存删除，无法核对”。

- 股市广度的新高新低与均线直接用 TuShare 计算的因子，本节核的是系统对这些因子的汇总，不核因子本身。
- 选源规则，即多源取值不一致时该取哪个来源，不在本节范围。

### 派生数据：多源备注与资讯声明的读取排除（体检票 17）

实现在 `tools/quality/derived.py`（`excluded_news_claims`、`split_note`、`Observation.pick`）。

**生产的做法**：资讯、媒体与 AI 值入库时保存匹配原话（`claim_matched_quote`）。生产读取时按当时的规则重读原话，原话已不再给出这个值的声明，既不列为观测的候选，也不会被选中；声明本身照旧保存，以后的规则可以重新判定（lookback 20，`.scratch/lookback-fetch-gaps-20261008/issues/20-pre-fix-local-news-claims-still-candidates.md`）。所以本节备注不应把这类声明列为多源中的一方。

**适用范围**：只影响本节“多源”备注中列出的候选值和多源计数，不改变重算用哪个值。

- 有系统所选的声明（血缘）时，照旧用它重算，即使它属被排除的声明。历史投影的冻结血缘照旧重算。所选声明属被排除的声明时，它的值不算多源的一方，备注另写“按系统所选 X，该声明属按读取规则排除的资讯声明（原因）”；所选声明的值为空时，也照样注明原因。
- 没有系统所选时，回退口径不变，仍按全部可用声明：取值唯一才用，否则不用。若取值不唯一只是因为有被排除的声明，备注写“无系统所选可依：可用声明取值 …，其中 … 属按读取规则排除的声明”。这种情况不算多源，不计入多源计数。
- 只有下列规则判出的声明才算被排除，“未被选中”不等于被排除。例如媒体值经复核后未被选中的一方（ADR-0039 第 4 条），仍是候选，照常列入备注。
- 规则按体检时库中保存的内容判定，窗口内各日一律适用，不按时点回溯。这与生产“按当时的规则读”一致。

**被排除的资讯声明**：只看 `claim_matched_quote` 里有记录的来源声明。依次判下列三条，取第一条适用的作为原因。三条都只用库里保存的页面标题、网址和主语子句判定，不重读原话。凡判为排除的，生产也一定排除：无论原话是否还给出这个值，生产都不采用（第 3 条：原话还给出值时，按嫌疑声明不采用；不再给出时，按原话不成立不采用）。

| 分母 | 来源 | 计数单位 |

### 追溯断链

输入编号既联接不到 `source_claim.claim_id`，也联接不到 `derived_observation.derived_observation_id` 的，单列为追溯断链，不算缺失。核心输入包括 120 日窗口之前用于均线、斜率和持续确认的观测；按留存规则，三核心价格的窗口前声明即使被投影引用也可删除（`retention.py`）。本节会注明核心断链中有多少不在三核心窗口观测之内；宏观断链不适用这条留存例外，出现时需单独查明。

核心断链再按下一节的规则逐个恢复，分两类报告：**声明行已删除、已从原件精确恢复并核验**；**无法恢复、未核验**（再分“未命中”与“有歧义”）。报告列出各核心指标恢复的个数、首末日和所用回执（至少恢复出一个编号的回执），没通过校验的回执写明没通过哪一项。

### 三核心窗口前冻结编号的精确恢复

出处：2026-10-11 用户决定（残余票 03，方案 B，`.scratch/residual-triage-20261011/issues/03-core-pre-window-inputs-untraceable.md`）。不扩大留存，ADR-0022、0035、0040 不变，生产不改；体检用回执原件逐个重建被删声明的编号，命中即为已核验。实现在 `tools/quality/core_trace.py`，第二层与第三层（二）共用。

**范围**：被审运行 `core_assets.model_input_observation_version_ids` 中联接不到 `source_claim` 的编号。

**候选回执**：本运行在 `full_run_acquisition` 登记、并经 `source_claim_acquisition` 与该核心指标现存声明关联的回执（与第三层（二）读原件的是同一组）。逐份校验，任一项不满足，该回执不参与恢复，报告写明原因：

1. **原件哈希**：原始件（`raw_hash`）与规范化件（`normalized_hash`）都在制品库里，内容的 SHA-256 等于登记的哈希。
2. **来源身份**：回执的 `provider` 为 `tushare`，参数带 `ts_code`；规范化件每一行的 `metric_id` 都是该核心指标、`source_code` 都等于参数 `ts_code`；关联的现存声明 `provider` 为 `tushare`，`period_start` 等于 `period_end`，`source_reference` 都等于 `tushare:<api_name>:<ts_code>:<period_end>`。
3. **截止时间**：回执在截止前发起、取得应答并通过校验（有原件，状态为 `validated`，`started_at`、`received_at`、`validated_at` 都不晚于截止），声明的入库时间（见第 5 项）也不晚于截止。时间都解析为带时区的时刻再比较，不按文本比较；候选回执不经公共读取（`Run.receipts`：它在任何校验之前就解析每份回执的请求参数），请求参数在逐份校验时才解析，参数损坏只让这一份回执不用。
4. **原始件与规范化件取值一致**：原始件是 TuShare 结构（`data.fields/items`），每个 `trade_date` 只出现一次，收盘 `close` 是有限数（布尔值不算数）；规范化件是顶层数组，每个 `business_date` 只出现一次，`close` 也是有限数；两者的日期集合相同，同一天的 `close` 数值相等。
5. **声明模板唯一**：关联的现存声明在 (`definition_version`, `period_kind`, `dimensions_json`, `value_state`, `public_available_at`, `available_at`) 上只有一组取值；不唯一时记“有歧义”，该回执不用。`available_at` 是整批声明写入时取的同一个时钟（`evidence.py` 的 `availability_clock`），一批里所有声明共用，不是回执的 `validated_at` 或 `received_at`，不能拿后两者代替。
6. **现存声明自检**：每条关联的现存声明，其 `value` 必须等于原始件当日收盘；再按下面的规则用该收盘重算编号，必须重现库中的 `claim_id`。任一条不满足，该回执不用（报告写明是值不一致还是“编号规则未重现现存声明”）。结构异常（字段类型不对、时间缺时区、数值溢出等）同样记为不用，不中断体检。

**编号规则**：抄录自生产代码 `src/pring_cycle/evidence.py` 中写入声明的 `_append_source_claim` 与 `_stable_hash`，只作为文档化的规则，脚本不导入生产代码。

- `H(a, b, …)`：各部分用 U+001F（单元分隔符）连接，按 UTF-8 编码后取 SHA-256，写成十六进制小写。
- 观测编号 `observation_id = H(metric_id, definition_version, period_kind, period_start, period_end, dimensions_json)`。三核心是 `business_day`，起止都是该交易日的 ISO 日期，`dimensions_json` 为 `{}`（按键排序、不转义非 ASCII 的 JSON）。
- 声明编号 `claim_id = H(observation_id, provider, source_reference, value_state, repr(value), public_available_at, available_at)`。`provider` 为 `tushare`；`value_state` 为 `reported_value`；`value` 是原始件当日的 `close`，按 Python 浮点数的 `repr` 写（最短往返表示，如 `231.0961`）；两个时间都是 UTC 的 ISO 文本（`isoformat()`，带 `+00:00`），与库中存储的文本相同，为空时取空串。TuShare 的核心应答没有可靠的发布字段，三核心声明的 `public_available_at` 为空。
- `period_start`、`period_end`、`source_reference`、`value` 逐日取自原始件，其余各项取自第 5 项的模板。

**匹配**：通过校验的回执，对原始件的每一天按上式算出编号，落在断链集合里的就是“已从原件精确恢复并核验”，同时得到该编号对应的日期和收盘值。同一个断链编号被不同的（指标，日期，值）命中，记“有歧义”，不算恢复；没有任何一天命中的记“未命中”。两类都“无法恢复、未核验”。

**第三层（二）的用法**：已恢复的编号按其日期与收盘值直接进入冻结核心序列，不再注“不能逐一对应”。全部恢复时不再补读任何原件日子（原件覆盖得比冻结集合更早也不影响）。仍有未恢复的编号时沿用原办法：从同一批原件补读已持有首日（声明与已恢复的日子中最早的一天）之前的日子，补读条数必须等于未恢复的编号数，否则报告“未重算”；这部分照旧注明只能按条数与日期推定、未核验。

**局限**：

- 只用本运行自己的核心回执。一份回执关联的现存声明全被清理时，模板（尤其 `available_at`）无从得知，这份回执的编号只能记“未命中”。实测：旧运行 `run-dc0bb2d9db7068bf552d` 按本节规则独立重建，冻结核心编号 536 个，断链 191 个，恢复 135 个，余下 56 个属于这种情况，无法恢复（体检票 07 的分流取证，2026-10-12；该运行的冻结清单没有 `confirmation_rules`，`audit.py` 不能直接体检它）。

**库存象限三条线**（模型规则补全批次票 05）：规则按生产现行做法写成，用户在 2026-10-11 访谈中决定纳入体检（`.scratch/model-rules-validation-20261011/interview.md` 的 Q10；取证见同目录 `codex-facts-20261011.md` 第 7 条；三线、共同月份、两种未分类的原始取舍见 `.scratch/macro-semantics-20261006/issues/08-inventory-quadrant-and-warrants.md` 的“解释性取舍”第 1–3 条）。体检只依据下列规则，从投影成员的取值独立判断，不沿用系统的成员标注。

- **规则来源**：冻结清单 `confirmation_rules.key_indicators` 中带 `quadrant` 的关键指标（v0015 为 `inventory_quadrant`）。`quadrant.lines` 恰为需求 `demand`、生产 `production`、库存 `inventory` 三条线，各有一个主成员 `main` 和若干辅成员 `auxiliary`，各线 `auxiliary` 为列表（可省略），主成员与辅成员都是对象，成员名称（`name`）是非空字符串且各不相同，不满足时报告冻结规则不全、不再往下核；`quadrant.quadrants` 是象限名到三线方向的表。成员按指标编号与完整维度对应冻结清单。v0015 的成员如下（需求与库存方向定象限，生产验证）：

| 线 | 主成员 | 辅成员 |
|---|---|---|
| 需求 | PMI 新订单（`CN_PMI_ACTIVITY`，`series=new_orders`） | 工业企业营业收入累计同比（`CN_INDUSTRIAL_FINANCE`，`item=revenue`） |
| 生产 | 工业增加值当月实际同比（`CN_INDUSTRIAL_VA`；2 月以 1—2 月累计同比代替） | PMI 生产（`CN_PMI_ACTIVITY`，`series=production`） |
| 库存 | 产成品存货名义同比（`CN_FINISHED_GOODS_INVENTORY`） | PMI 产成品库存（`CN_PMI_INVENTORY`）；产成品周转天数同比变化（`CN_INVENTORY_TURNOVER`） |

- **投影里的成员**：关键指标的成员中有一个是象限本身（`name = quadrant`，不带维度，不带 `line`，标 `main`，`values` 为空），其余是各线成员，带 `line` 字段。三个线主成员也标 `main`。
- **象限月**：取三个线主成员各自最新一期中最早的那个月，先发布的线（如月末发布的 PMI）等其他线。所有成员都只读象限月和前一象限月，缺月不退回更早的月份。前一象限月是上一个月，但要跳过任一线主成员 `unreleased_months` 中的月份（v0015 为 1 月，所以 2 月的前一象限月是上年 12 月）。体检核对：每个成员持有的期次（`periods`）加上缺的月份（`missing`），恰好是这两个月；两者都为空的成员不算错位：它根本没有可显示的证据，或者象限月无法确定（任一线主成员没有最新一期时，象限月为空，所有成员都不读）。象限月以象限成员的 `period`（象限月月末）为准。
- **方向**：成员的动量由两期取值比较得出：后值 − 前值大于容差 max(|前值| × 1×10⁻⁹, 1×10⁻¹²) 为 `up`，小于负容差为 `down`，其余为 `flat`；不足两期为未知。库存象限的成员都按动量比较：`agrees_by` 应为 `momentum`，`momentum` 与 `direction` 都应等于重算的动量；取值不是有限数值的，动量为未知。
- **象限**：任一线主成员的证据状态不是 current、有缺月或方向未知时，象限未知：`quadrant = unclassified`，`unclassified_by = insufficient`。否则，三线方向在 `quadrants` 表里的，为对应象限，`unclassified_by` 为空；不在表里的（含持平、生产与需求反向），为 `unclassified`，`unclassified_by = inconsistent`。象限成员的 `lines` 逐线给出主成员的名称、冻结标签、期次与方向。象限成员的证据状态取三线主成员中第一个不是 current 的状态（按需求、生产、库存的顺序），都是 current 时为 current。象限成员的 `missing` 按同一顺序逐线列出：状态不是 current 时为 `线:维度:状态`，每个缺月为 `线:维度:月份`；维度按键排序写作 `键=值`、逗号相连（无维度时用成员名称），重复的只留一条。
- **主辅比较**：每个辅成员只与本线主成员比较。辅成员的证据状态不是 current，或任一方方向未知，为 `unknown`；方向相同为 `agrees`；有一方持平为 `flat`；一升一降为 `opposes`。只看辅成员的证据状态，主成员只看方向。
- **分化识别**：象限未知（`unclassified_by = insufficient`）时为 `unknown`；否则有一个辅成员为 `opposes` 即为 `divergent`，没有为 `consistent`。`unclassified_by = inconsistent` 的象限三线方向都已知，照常判断。上文的“分化当且仅当独立判为分化”与“分化封顶”两项检查改用这里的判断。

比对方法：期次、动量、三线读数、象限四元组（证据状态、缺项、象限、未分类原因）、各成员的线与标注、关键指标的 `consistency`，全部要求与独立判断完全相同。结论中逐个写出象限月、三线方向、象限和各辅成员的比较结果。

局限：

## 第三层（二）：三核心独立重算

`tools/quality/core_recompute.py` 从被审运行冻结的核心输入出发，按文档写明的规则重算每一天的债、股、商品趋势状态、资产候选和正式阶段，并与系统输出逐日比对。规则清单、每条的出处、已登记的歧义及其裁决见[票 04](../../.scratch/data-quality-audit-20261010/issues/04-core-independent-recompute.md)。实施者声明：实现只依据文档与冻结清单，没有读过、也没有调用生产代码中的趋势和阶段计算。

**输入**：被审运行 `core_assets` 数据集里的 `model_input_observation_version_ids`。

- 能追到 `source_claim` 的编号，直接取声明值。
- 追不到的是窗口前的预热输入：按 ADR-0035，三核心价格不因被投影引用而保留，运行结束后被留存清理。它们先按第二层“三核心窗口前冻结编号的精确恢复”逐个重建编号，命中的按其日期与收盘值进入序列，记为已核验（输入表“原件精确恢复”列）。仍未恢复的，从本运行自己的核心回执原件补读（回执经 `source_claim_acquisition` 与该核心指标的声明关联），只补读已持有首日之前的日子，补读条数必须等于未恢复的编号数，否则本节报告“未重算”；这部分只能按条数和日期推定为被冻结的那批预热输入，报告会注明未核验（输入表“原件推定补读”列）。
- 与声明重叠的日子，核对原件收盘价是否等于声明值。

**收益链**：按官方 `change/pre_close` 收益链构造价格水平（`pre_close` 取自原件）。原件 `pre_close` 与上一条收盘不相等的日子记为断点，断点照常参与计算。以下两种情况下，收益链无法按文档构造：序列中间缺了一个上交所开市日（生产按核心沿用或窗口缺日处理，见下方“核心沿用”），或者某一天缺 `pre_close`（生产按相邻收盘之比计算收益，不读 `pre_close`）。本节尚未按这些做法重算，所以从这一天起的所有日子都不重算，记为“未核验”。状态机带有记忆，后面的日子也会受影响。

**规则要点**（参数取自冻结清单的 `trend_rules`）：

- MA120 为含当日在内 120 个有效观测的简单均值；斜率为 MA120(t)/MA120(t−20)−1；噪声带为 1.5 倍最近 20 个日收益的总体标准差。
- 牛向条件：距离 ≥ 噪声带，且斜率 > 0。熊向条件：距离 ≤ −噪声带，且斜率 < 0。
- 与稳定方向不同的方向条件构成候选，连续 8 个观测成立后确认。条件中断时候选清零，稳定方向保留。首次确认之前，状态为空。
- 三核心状态按 `stage_mapping` 映射，键的顺序为债、股、商品。阶段从冻结输入的第一天起逐日推进，所以上一确认阶段也计入窗口前的可见历史。
- 某个核心当天没有观测（核心缺日）时，该日不重算，记为“未核验”；收益链中断时的处理见上一段。

**核心沿用（A5）**：以下是生产的现行做法，2026-10-11 访谈（[Q4](../../.scratch/model-rules-validation-20261011/interview.md)）认可按现状，取证见[同批取证](../../.scratch/model-rules-validation-20261011/codex-facts-20261011.md)第 2 条。本节尚未据此重算沿用日。

- 条件：某核心在某天（目标日或补算日）没有观测，而它最新的观测正好在上一个开市日，即只落后 1 期，并且照常通过其余检查：这一天之前、120 个开市日内的每个开市日都有观测，没有冲突，身份、数值与原件核对都通过。落后 2 期及以上不沿用：上一开市日本身就是窗口内的缺日，报 `window_session_missing`。
- 计算：把上一开市日的收盘作为这一天的临时点，追加到该核心序列末尾，当日收益（与上一点之比）为零。MA120、20 日斜率和 1.5 倍 20 日收益标准差的噪声带都含这个临时点重新计算，方向条件照常判断，所以沿用日同样可以推进候选计数，也可以完成确认。
- 输出：得出稳定方向时 `reason` 为 `carried_forward`，`carried_forward` 为真；没有稳定方向时 `reason` 取趋势本身的原因，`carried_forward` 为假。临时点不写成声明、不入库，也不列入模型输入编号。
- 恢复：之后的运行按真实序列从头计算。缺的那天补齐后，自然接回；如果它一直缺，而且落在后面某天的 120 个开市日窗口内部，那一天就报 `window_session_missing`，不会一直沿用下去。

**系统输出**：取被审运行投影中 `stage_history` 的全部记录。同一天可能有多条记录，来自更早的运行和模型。目标日另外比对本运行的 `p0_assessment` 和 `cycle_overview`，缺少其中任何一项都会写明。比对的字段为：

- 各资产的 `state`、候选（`candidate_state`、`candidate_days`）；
- 测量值（`distance_pct`、`noise_band_pct`、`slope_pct`），相对容差 1e-9；
- (`current_stage`, `last_confirmed_stage`) 二元组；
- 是否为非典型组合（`stage_reason`）。

报告还核对这些记录所属模型的趋势规则、阶段映射与冻结清单是否相同。

**每日结论**：

| 结论 | 含义 |
|---|---|
| 一致 | 所有字段一致 |
| 有差异 | 至少有一个字段不一致 |

**差异归因**：已汇总的日子不再重算，所以窗口前部的日汇总是早先的运行按它当时持有的历史算出的。对来自早先运行的记录，如果有差异，就取那次运行自己的核心回执原件（接口与 `ts_code` 和被审运行相同，截至其目标日），按同一规则复算一次。复算与记录一致时，再看两份输入的关系：那次运行的原件起点早于冻结输入、且重叠日价格相同的，记为“起算点不同”；否则记为“早先输入不同”（原因待查）。复算仍不一致，或原件已不可读的，记为“未解释”。复算中只在可见历史之前的阶段上有分歧的，原因栏会注明“可见历史之前的阶段未核验”。
