# 完整套件只在显式冻结节点运行

完整套件的唯一产物是某个冻结版本的验收收据。材料身份键覆盖源码，因此源码一经改动，上一次
的收据立即失效。在开发过程中运行完整套件，得到的收据从产出那一刻就在贬值：它证明的是一个
已经不复存在的版本。

2026-09-18 至 09-20 的实际记录说明这不是理论风险。三天内完整套件被启动九轮，合计 14.4
小时；其中六轮以失败或环境中断结束，占 6.7 小时。更关键的是 v7 已于 09-19 成功，其后仍
运行了 v8 至 v11 四轮，因为期间源码继续改动，收据反复作废。同期已经存在"按变更影响触发
重型验收"的约定，但它依赖每次都做出正确判断，九轮的事实说明这一约定挡不住。

因此完整套件改由显式冻结声明触发：`tools/check.py full` 在没有 `--freeze` 时硬性拒绝并
说明理由，日常反馈使用 `tools/check.py quick` 加相关测试文件，受变更影响的重型验收单独
显式运行。判定冻结与否由人做出，不由工具推断工作区状态：推断会猜错，而猜错时挡住的是一次
真正需要的收据。

这一选择牺牲"任何时刻都能顺手跑一次全套"的自由，换取每一次 1.7 小时的等待都对应一份不会
立即作废的收据。它不降低任何功能门禁或产品性能硬门，也不改变默认的 pytest 完整发现范围：
被改变的只是**何时**值得付出这段等待。若将来材料身份键不再覆盖源码，或完整套件的耗时降到
可以随手运行的量级，这一决定应当重新评估。
