1. **条件触发：历史缺格未补齐且仍在窗口内时反复出现。** 仓单没有进入确认度计数成员，`warrant_conversions` 驱动库存附注及供需观察，读取的是窗口内各品种共同持有的首尾日，并非最新几期；本次首尾为 04-14、10-12，因此这些中间缺格不改变首尾变化读数，但减少 `days_held`（[registered_warrants.py:139](/mnt/d/cursor/datasourceRF/src/pring_cycle/registered_warrants.py:139)、[context_projection.py:709](/mnt/d/cursor/datasourceRF/src/pring_cycle/context_projection.py:709)）。每轮仍按品种请求覆盖这些日期的区间，`warrant_day_empty_in_run_answer` 只省掉**本轮区间应答之后的单日重复请求**，不跨运行缓存空结果（[worker.py:1911](/mnt/d/cursor/datasourceRF/src/pring_cycle/worker.py:1911)、[targeted_context.py:52](/mnt/d/cursor/datasourceRF/src/pring_cycle/targeted_context.py:52)）。未补齐时，体检及最终计划会持续列缺格，但不能说生产总览缺口清单也一直列出：只读核对 `run-0a8dabc2…` 的 `cycle_overview.gap_list` **没有仓单项**，其生成逻辑跳过 current，且不把所有历史计划缺格直接并入（[full_retrieval.py:596](/mnt/d/cursor/datasourceRF/src/pring_cycle/full_retrieval.py:596)、[freshness.py:862](/mnt/d/cursor/datasourceRF/src/pring_cycle/freshness.py:862)、[freshness.py:1027](/mnt/d/cursor/datasourceRF/src/pring_cycle/freshness.py:1027)）。按已存 SHFE 日历代估中国交易日，07-21、09-09 分别从目标日 **2027-01-14、2027-03-12** 的120日窗口移出，最终以届时 SSE 日历为准。**对模型输出的影响：有（完整性与持有天数字段；对10-12的正式阶段、确认度计数和仓单首尾变化读数无影响，未来缺日成为窗口端点时可能改变比较起点）。**

2. **条件触发：发布滞后会反复出现，但不能认定每次真实运行都未发布。** EIA 虽有日频观测，时效注册却按周频、周日归期、发布滞后2个 SSE 交易日、北京时间23:00、宽限7个交易日计算；这是推定规则，本地接入文档明确实际发布日期可变、没有逐日精确发布钟点，所以 T+1 09:00 是否已发布不能一概否定，尤其跨中国休市时（[freshness.py:53](/mnt/d/cursor/datasourceRF/src/pring_cycle/freshness.py:53)、[freshness.py:187](/mnt/d/cursor/datasourceRF/src/pring_cycle/freshness.py:187)、[freshness.py:250](/mnt/d/cursor/datasourceRF/src/pring_cycle/freshness.py:250)、[eia-html-contract.md:63](/mnt/d/cursor/datasourceRF/.scratch/pring-data-acquisition-repair/eia-html-contract.md:63)）。目标日补缺门禁按该日所属周的推定发布时点判断，故目标日截止下容易固定出现 awaiting_release，它不是上游尚未发布的实证（[worker.py:951](/mnt/d/cursor/datasourceRF/src/pring_cycle/worker.py:951)）。没有确认度成员读取 EIA，只有商品观察接口读取 WTI、Brent 的最新可见值及前值；本次实际两项都读 **10-06**，批次时效和观察行均为 **current**，并非成员未确认，也不保证只落后一期（[confirmation.py:3523](/mnt/d/cursor/datasourceRF/src/pring_cycle/confirmation.py:3523)、[context_projection.py:2787](/mnt/d/cursor/datasourceRF/src/pring_cycle/context_projection.py:2787)、[freshness.py:688](/mnt/d/cursor/datasourceRF/src/pring_cycle/freshness.py:688)）。**对模型输出的影响：有（商品观察接口显示较旧油价并保留目标日缺口；不改变正式阶段或确认度计数）。**

3. **结构性每次都会出现：在沿用当前发布时间推定与目标日截止的正常 T+1 路径中。** 融资合计登记为下一交易日09:05发布，而生产计划和投影确实将公开可见时间限制在目标日结束，所以即使运行到09:05以后并取得目标日值，也仍选上一期，这不是体检自行加的限制（[freshness.py:134](/mnt/d/cursor/datasourceRF/src/pring_cycle/freshness.py:134)、[full_run_requirements.py:70](/mnt/d/cursor/datasourceRF/src/pring_cycle/full_run_requirements.py:70)、[context_projection.py:1939](/mnt/d/cursor/datasourceRF/src/pring_cycle/context_projection.py:1939)）。但我认为不能无争议地称为符合 T+1 意图：ADR-0041 为等两融等数据而移到次晨，并规定“运行时仍未发布”才暂用上一期，现有截止却将运行时已经发布的数据也挡住，存在设计口径冲突（[ADR-0041:11](/mnt/d/cursor/datasourceRF/docs/adr/0041-scheduled-run-identifies-previous-trading-day-next-morning.md:11)）。应答若仅请求末日缺 SSE 或 SZSE，则整日不产出两项合计、保留其他完整日期；若更早日期有半边缺失，则抛出 `tushare_margin_exchange_coverage_incomplete`，绝不把半边当全市场合计（[tushare_context.py:1635](/mnt/d/cursor/datasourceRF/src/pring_cycle/tushare_context.py:1635)）。**对模型输出的影响：有（融资观察值滞后；体检“上一期算完整”不表示采用了目标日值，也不影响正式阶段或确认度计数）。**

4. **条件触发：运行冻结时已跨过当天发布时点、却仍只持有目标日数据时出现。** 这是**生产判定与文档契约不一致**：生产要求 `held >= released` 才 current，`held >= due` 但低于 released 时记 awaiting_release，而 CONTEXT 明写持有应有期为 current（[freshness.py:359](/mnt/d/cursor/datasourceRF/src/pring_cycle/freshness.py:359)、[CONTEXT.md:262](/mnt/d/cursor/datasourceRF/CONTEXT.md:262)）。本次冻结在10-13 12:31，五项均满足 `held=due=10-12 < released=10-13`，应有期并没有被重算成10-13；体检只是直接读取表中状态（[worker.py:543](/mnt/d/cursor/datasourceRF/src/pring_cycle/worker.py:543)、[tools/quality/model_input.py:439](/mnt/d/cursor/datasourceRF/tools/quality/model_input.py:439)）。如果冻结在09:15或12:00发布时点之前，相应指标不会仅因这个原因变为 awaiting_release。**对模型输出的影响：无（本次成员读数仍按 `period_status` 记 current；受影响的是批次时效标签，[freshness.py:688](/mnt/d/cursor/datasourceRF/src/pring_cycle/freshness.py:688)）。**

5. **条件触发：旧发布仍落在新运行的证据窗口内时继续计数。** 79项计的是历史“发布到首次入库超时”，补齐后迟到事实不会消失，但体检只遍历发布时间位于窗口起点至截止之间的期次，所以新运行窗口前移会逐项退出，固定旧报告不会自行归零（[tools/quality/acquisition.py:1119](/mnt/d/cursor/datasourceRF/tools/quality/acquisition.py:1119)、[tools/quality/acquisition.py:1164](/mnt/d/cursor/datasourceRF/tools/quality/acquisition.py:1164)）。这79项最晚发布为2026-09-21，按已存 SHFE 日历代估，到目标日 **2027-03-24** 全部退出；这只保证该批旧项清零，不保证届时没有新超时项。它们是初始化补历史造成的迟到统计，对当前运行健康判断主要是噪音，不直接进入生产缺口清单，生产清单依据当前时效、选值及取数状态生成（[freshness.py:833](/mnt/d/cursor/datasourceRF/src/pring_cycle/freshness.py:833)）。**对模型输出的影响：无。**

6. **结构性每次都会出现：限于当前模型、来源可用且新目标日尚未持有的正常日常路径。** `basket_scalars` 在判断持有情况前无条件进入四所日历预检，随后才发现窗口不完整并走原流程，因此正常应答下额外4次请求不可避免；同日重跑、未配置来源或预检中途失败等不属于该前提（[basket.py:160](/mnt/d/cursor/datasourceRF/src/pring_cycle/basket.py:160)、[basket.py:274](/mnt/d/cursor/datasourceRF/src/pring_cycle/basket.py:274)、[worker.py:1873](/mnt/d/cursor/datasourceRF/src/pring_cycle/worker.py:1873)）。需纠正计数单位：**24与20是篮子总请求数**，本次为8次 `fut_basic`＋8次 `fut_daily`＋8次 `fut_trade_cal`，日历请求是8对4（[acceptance-20261013.md:181](/mnt/d/cursor/datasourceRF/.scratch/model-rules-followups-20261012/acceptance-20261013.md:181)）。先以 `end_date in held_levels` 作为进入预检的必要条件即可消除新目标日的4次开销，未持有时直接走原流程，已持有时仍须完整预检才能判全窗口持有。**对模型输出的影响：无（正常成功路径只改变请求成本和耗时）。**

7. **条件触发：墙钟回拨跨过所比较的两个时间点。** 触发不只“校验早于接收”，还包括“接收早于请求开始”，以及时间缺失时区；同一 `acquire_scalars` 家族在全部回执校验完之前不入库，一次异常会中断整组入库，但不等于整次 Worker 运行全部拒收（[acquisition.py:460](/mnt/d/cursor/datasourceRF/src/pring_cycle/acquisition.py:460)、[acquisition.py:579](/mnt/d/cursor/datasourceRF/src/pring_cycle/acquisition.py:579)、[acquisition.py:683](/mnt/d/cursor/datasourceRF/src/pring_cycle/acquisition.py:683)、[tushare_context.py:392](/mnt/d/cursor/datasourceRF/src/pring_cycle/tushare_context.py:392)）。本地失败本身没有负缓存，下一轮可重取，但并非无代价：已经发出的请求仍计配额，还耗费时间并留下失败回执（[retrieval_ledger.py:843](/mnt/d/cursor/datasourceRF/src/pring_cycle/retrieval_ledger.py:843)、[tushare_quota.py:157](/mnt/d/cursor/datasourceRF/src/pring_cycle/tushare_quota.py:157)）。10-14 09:00若只是家族取数失败，Worker会继续补缺，核心仍不足时可以完成并输出 `core_data_pending`、不给正式阶段，并不必然成为运行失败（[worker.py:1981](/mnt/d/cursor/datasourceRF/src/pring_cycle/worker.py:1981)、[p0.py:412](/mnt/d/cursor/datasourceRF/src/pring_cycle/p0.py:412)）。**最坏不能保证降级完成**：若回拨使冻结截止早于运行初始截止，会抛错并进入可恢复的 `action_required`，本轮无法正常完成（[runs.py:686](/mnt/d/cursor/datasourceRF/src/pring_cycle/runs.py:686)、[worker.py:351](/mnt/d/cursor/datasourceRF/src/pring_cycle/worker.py:351)）。**对模型输出的影响：有（可能缺失辅助读数、沿用核心、无法给出正式阶段，严重时本轮不能完成）。**

8. **结构性每次都会出现：成功运行执行这处清理调用时都不保存返回结果。** Worker先完成报告并将运行标为 completed，再直接调用 `prune_to_window(paths)`，确实没有接收或写入 `RetentionResult`（[worker.py:672](/mnt/d/cursor/datasourceRF/src/pring_cycle/worker.py:672)）。该返回对象只有窗口、各表删除数量、原件数量和回收字节数，甚至不是逐条删除明细，因此保存它能改善清理追溯，也仍不足以完整还原“删了哪些记录”（[retention.py:58](/mnt/d/cursor/datasourceRF/src/pring_cycle/retention.py:58)）。**对模型输出的影响：无（遗漏清理结果记录发生于报告完成后；影响事后追溯，实际留存删除造成的原料断链是另一问题）。**
