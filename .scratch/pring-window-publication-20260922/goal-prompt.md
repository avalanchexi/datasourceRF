## 严格执行开发流程

遵循 ask-matt 的主流程：grill-me/grill-with-docs（grilling）→ to-spec → to-tickets → implement（在已批准的测试入口执行 TDD）→ code-review → 按项目既定规则提交与验收。TDD 按当前技能执行红—绿循环，重构放在审查阶段。执行技能时读取对应 SKILL.md 的实际要求，不能仅声称使用过技能。

本仓库的访谈入口采用 grill-with-docs：它与 grill-me 使用相同的 grilling 访谈机制，并将决定保存在领域文档和 ADR 中。本轮访谈、规格及 19 票拆分已经由我确认，请直接从 implement 开始，不重复询问已决定事项，也不为每张票重新生成规格。

每张实施票在独立上下文中读取完整规格、本票和直接前置的实际交付，使用 implement，在已批准的公开入口采用必要的 TDD 红—绿循环；复用已有有效测试，不补机械镜像测试。完成后通过 code-review 的 Standards 与 Spec 两轴审查，在审查阶段处理必要重构，修复实际问题并由主代理核验结果。提交与收据时机遵守项目现有约定，保留本轮无关的未提交改动。

只有出现尚未决定、确实影响产品含义或范围的新问题时，才回到 grill-with-docs：先自行查实可查事实，再一次提出当前决策前沿的问题，给出推荐及代价。明确受该问题阻塞的票，继续其他可执行票。范围变化落实到规格/ADR及任务后再执行依赖该决定的工作。

## 并行实施授权与隔离

我明确允许本目标中的独立任务并行实施。以下规则针对本目标，替换旧委派文档中“子代理只能只读、不得改源码或跑测试”的限制：**只有已经验证隔离有效的实施子代理，才可以在自己的工作树中改代码并运行获准的定向测试。** 其他项目约定继续生效。

Codex 担任主代理，不依赖 Claude Code 恢复额度。子任务仍只通过直接的 codex exec CLI 调用，继承现有模型和推理配置，不使用其他委派封装。最多同时运行 3 个子任务，资源不足时减少；并行是上限，不是必须凑满的配额。

实施前由主代理为每个子任务准备并核验：

1. 独立 Git 工作树、分支和明确的当前源码基线。工作树必须包含该票需要的已批准未提交变更、任务文档及材料；不能仅检出 HEAD 后假定与当前工作区一致。
2. 独立虚拟环境和实际安装的包副本；核对测试子进程实际导入身份，禁止操作主工作区或其他任务的共享安装。
3. 独立的可写数据库、CAS、测试临时目录和运行输出。只可复用已核验且不可变的只读材料；运行库及磁盘位置遵守项目测试约定。
4. 明确读写范围、基准版本、测试权限和交付物。子代理不能修改其他工作树、领取或关闭其他票，不能自行改变正式模型指针。

只读调查使用 read-only 沙箱；通过隔离核验的实施任务才使用限定工作树的写权限。若当前工具不能提供可靠隔离，自动改为并行只读调查、主代理串行实施，报告具体限制，不把共享环境中的竞争写入当作并行方案。

## 自主推进与完成标准

对已批准的票、普通实现选择、必要验证和可复用材料核查自主推进，不逐步重复请求许可。需要新的业务选择、外部凭据、超出既有预算或具体生效/切换授权时，先完成其他已授权准备，提出具体且可审阅的问题，说明对应阻塞。

真实取证遵守现有来源、凭据及调用预算，保存原件、实际获取时间和失败分类。不得将沙箱网络错误判作来源不可用，也不得用抓取时间、计划发布时间、模板时间或未知版本填充历史 PUBLIC。没有新证据时不反复重试已失败路径。

某票被外部证据阻塞时，记录缺什么、查过什么、影响哪些结果及解除条件，继续其他就绪任务。没有可推进工作时保存准确检查点并报告阻塞；Goal 状态按宿主规则处理，不用虚假完成结束目标。

每个阶段边界更新任务和续接记录，包含实际在途任务、已完成交付、有效收据、阻塞条件和下一步。主代理尽量保持协调上下文；子任务使用新上下文。需要压缩时在阶段边界保存决定与证据索引，不能只保留“已通过”摘要。

只有全部必要验收、真实材料、回放、运行及要求的显式操作均有有效证据，才把整体目标标为完成。结束时报告实际完成票、尚未完成项、验证证据和最终运行状态。

首次执行时，先核验工作区、环境和任务前沿，给出首批分派及串行验证安排，随后直接开始已获授权的工作。续接已有 Goal 时，先读取 execution-status.md 和 execution/dispatch.json，核验实际进程及终态，接收在途交付，再推进剩余任务；保持同一 Goal，不重复创建目标或派发已经在途的任务。
