# 31: TuShare 调用限额：每分钟节流与每日额度

**What to build:** TuShare 请求在发出前遵守按接口登记的每分钟频次；每日额度只依据本库已记录的请求计数，用尽后本轮不再请求该接口，记为未尝试；发出后被以每日额度拒绝的接口，本轮停用、下次运行最多试探一次。术语见 `CONTEXT.md`「调用限额」。

**Blocked by:** 22（40203 的限频与无权限区分、账本按适配器分类退避）

**勿并行：** 24、25、30（同改 Worker 取数）

**Status:** ready-for-agent

来源：用户访谈（2026-10-01，/grill-with-docs），排在 M7 真实运行之前。事实调查见 `scratchpad/ratelimit-survey.md` 与 TuShare 官网（[积分与频次权限对应表](https://tushare.pro/document/1?doc_id=290)）。

## 现状（调查结论）

- 真实撞过的只有 `major_news` 每日 40 次：9/24 第 5 页被拒（9/21 00:00—9/22 13:15 资讯缺失）、9/25 首页即被拒、9/26 有一页被拒；三次运行都照常完成。9/25 00:04 仍被拒，零点清零不成立，恢复规则未知。
- 没有可核实的每分钟超限事件；仓单那次 62 张失败回执是时钟回拨与上游空数据，不是限频。
- 首次完整取数约 400 次请求，日常约 100 次；补缺可放大（仓单最多再 720 次）。
- 官网只按积分档给每分钟频次与每日总量（120 积分：每分钟 50、每天 8000；200 积分：每分钟 100、每个 API 每天 10 万；500 积分及以上：每分钟 500），未说明并发。仓库存档的接口频次只有 `stock_basic` 每分钟 50、`daily` 每分钟 500。账号积分档未记录。
- 现有代码对 TuShare 没有任何节流或每日额度判断；取数在 Worker 主流程中串行。

## 已定决定（用户，2026-10-01）

- 目标：完整运行不撞每分钟上限；每日额度撞到就停、记清、下次补齐。不追求"永不撞限"。
- 主动停下（本地已知每日额度用尽）记为未尝试，原因"当日配额用尽"，不算获取失败；指标仍缺则按缺失列出。被来源以限频拒绝记为源失败（带业务码、分类为限频），缺口类别 fetch_failed。
- 限额登记在一处：按积分档与接口写明，档位变化只改这一处；未登记的接口按每分钟 50 次保守值。积分档由用户提供后填入。
- 每分钟节流按接口计（拒绝消息为"该接口"），留余量取上限的 80%；调用串行，不做并发控制。
- 每日额度只按本库回执计数，到登记上限的 90% 主动停；外部（测试、手工探测）消耗不可见，不另行登记。
- 每日额度被拒后不预设恢复时间：本轮停用该接口，下次运行最多试探一次。拒绝消息原文与时间照常记入获取尝试。
- 40203 消息明确为无权限时按无权限处理（与 HTTP 403 同规则，次日再试），缺口原因写"无权限"（票 22 实现分类）。

- [ ] 每日额度：本库计数到 90% 主动停，记未尝试；被以每日额度拒绝则本轮停用该接口、下次运行至多试探一次。

- [ ] 受影响测试经 `check.py quick` 通过；切片收尾冒烟通过；涉及 Worker 取数，另加跑完整目录正例。
