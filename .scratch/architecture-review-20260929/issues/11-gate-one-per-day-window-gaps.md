## 现状

- 目标日：`window_gaps` 取自最终计划中未完整的核心缺口，排除目标日（`worker.py:398`）。
- 补算日：不传 `window_gaps`（`worker.py:587`），`_core_readiness` 不会给出 `window_session_missing`，`evaluate_trend` 也不检查交易日连续（`domain/trend.py:62`）。窗口内缺一个核心日时，只要剩余历史够、最新值有效，补算日仍会发布正式阶段，与门①不一致。
- 不能把目标日的缺口集合直接给补算日用：会把该日之后的缺口算进去。

## Comments

- **口径核对**（Codex 只读调查，`t11-survey`）：
  - 计划认定的"缺"是"该期没有可采用的模型输入"，不是"没有回执"。依据选中、已验证、数值非空且家族复核通过的声明逐交易日判断。
  - 按可见序列枚举与此不完全一致，差在以下几处：
    - 有点但不可采用的日子（冲突、身份不符、原件复核失败、非数值）；
    - 窗口前端历史不足；
    - 补算日日历覆盖。
  - 真实缺行的目标日用例两种口径一致。原先用虚构 `window_gaps` 注入的迁移用例依赖计划参数。
- **用户决定（2026-10-01）**：
  1. 门①只看日期有无可见点。有点但不可采用的日子交给后续更具体的原因，仍阻断正式阶段。
  2. 窗口前端历史不足算历史不足：只从该日可见序列第一天往后枚举缺日，更早的部分由趋势报 `insufficient_history`。
  3. Worker 传入更宽的日历。补算日窗口超出覆盖时，该日记入补算失败清单、下次重试，不编造缺口。
- **实现**：
  - `TradingCalendar.sessions_to(day, count, *, since)` 只在来源覆盖范围内取交易日，不用工作日代替；`day` 越界或所需交易日早于覆盖首日时抛 `LookupError`。
  - `DaySummaries._core_readiness` 自行判断：截至该日的 120 个交易日（不早于序列首日，该日本身除外）里，有缺可见收盘的就报 `window_session_missing`。目标日与补算日共用。
  - `RunMaterials.window_gaps` 与 Worker 按计划组装的那段已删除。
  - Worker 另传 `window_calendar`，取冻结截止时点上交所日历里含目标日的连续覆盖段，只用于门①。
  - 按审查意见，作用域日历、前一交易日及时效判断仍用计划的 120 日日历，与运行缺口清单同一口径。
- **行为变化（均在授权内）**：
  - 目标日"有点不可采用"的原因码由 `window_session_missing` 改为对应的具体原因。
  - 前端历史不足改报 `insufficient_history`。
  - 直接调用模块、两期落后时，原因由 `stale_for_target_business_date` 改为 `window_session_missing`（前一交易日也缺）。
  - 以上都仍无正式阶段。补算日窗口内真实缺日现在会取消该日正式阶段，目标日读取的上次确认阶段可能随之变化，属于修正补算。
- **只记录、不修**：日常运行只补漏掉的少数几天，窗口外扩有限。如果留存清理后日历回执只剩 120 日，而可见核心序列更早开始，这些补算日会记为失败日，留待后续重试；目标日照常发布。首次初始化（280 天日历 + 160 点）的序列首日在日历覆盖内，不会大批失败。
