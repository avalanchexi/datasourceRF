# 数据库视图回归超时：根因与验证环境修正

2026-09-11。属于SQLite关联验证失败的诊断，不改变应用行为、测试断言或30秒上限。

## 观察到的失败

172真实终态为35通过、1失败/436.68秒，前后冻结输入校验通过。
唯一失败是`test_repeated_runtime_views_remain_available`子进程超时；
该子进程不调用本轮新增的Worker保留连接。不能直接把它判为SQLite锁再次失败，
也不能凭重跑一次通过抹掉原记录。

## 根因实验

- 173从原测试AST提取64轮公开调用，保留禁用GC、文件句柄128上限和30秒看门狗，
  只加每步计时、句柄观察及每5秒栈采样。实际超时；完成19轮时耗时29.40秒、CPU4.50秒，
  指纹计算累计25.34秒，其他11个步骤合计约0.65秒，19次句柄观测均为5。
  五次栈采样全部落在Windows挂载盘`site-packages/pring_cycle`的读取、扫描或stat。
  [耗时记录](verification-runtime-views-profile-173.json)、[运行栈](verification-runtime-views-stderr-173.txt)。
- 174只把实际安装包复制到测试卷ext4目录，复制前后核对全部95个非缓存文件，
  没有替换函数、返回值、数据库实现或依赖。子进程执行原测试字符串的完整64轮，
  相同30秒上限，实际4.42秒完成；源码、依赖、配置和数据库指纹完全相同。
  pytest 1通过/39.45秒（包含准备及文件逐项核验），前后冻结校验均0。
  [反事实记录](verification-runtime-views-native-174.json)、[真实终态](verification-worker-lifetime-terminal-174.json)。

这些结果支持的结论是：172中测试在30秒内无法完成的主因，是验证环境从DrvFS
重复扫描及读取应用包；不是已观察到的连接泄漏，也不是Worker保留连接的执行路径。
不据此断言过去每一次性能波动均来自同一原因，或应用在任意设备上都满足固定延时。

175在已有项目专属ext4镜像内另建验证虚拟环境，继续使用同一Python可执行文件、
原53个精确依赖版本以及当前冻结172的应用字节；依赖和包均离线安装。
源码仓库、旧环境、测试卷历史结果、应用指纹算法、测试循环次数及看门狗保持原样。
新的`run-native-175.sh`在挂载期间校验安装源、包95文件、依赖、Python及233输入/4保护文件，
测试结束后再次校验，随后卸载；测试失败也执行后验。它不使用PYTHONPATH来替代正式安装包。

建议Linux工作将频繁访问的文件放在WSL文件系统；此说明是环境选择依据，实际因果证据仍是173/174对照。

环境安装及同范围重验须以各自真实终态为准。174只是隔离变量的诊断，
不替代原用例、关联回归或默认全套；172失败记录完整保留。
