# 规格：数据质量体检脚本（取数完整、模型输入完整、模型输出正确）

2026-10-10 访谈定稿（用户逐题确认）。现状盘点见 [inventory-20261010.md](inventory-20261010.md)。

## 目标

做一组可反复运行的只读体检脚本，对**一次完成的运行**及其 120 日证据窗口回答三个问题：

1. 数据获取完整吗？
2. 输入 Pring 模型的数据完整吗？
3. 模型输出（正式阶段等）正确吗？

第一次正式使用：对 v0015 一次新的真实运行（目标日 2026-10-09）出体检报告，查出的问题逐条开票分流。

## 形态

- 先做体检，可反复运行；以后哪些检查值得固化进每次运行，另行决定，不在本规格内。
- 只出报告，不阻断运行，也不改运行库。
- 脚本放在 `tools/quality/`，只用 Python 标准库，用 SQLite 只读 URI（`mode=ro`）打开运行库，**不导入 `pring_cycle`**，以保持与生产实现相互独立。需要原件时，按内容哈希从运行库的制品目录只读读取。
- 脚本保持简练：一个入口命令 `python tools/quality/audit.py --run <run_id> [--database <path>] [--out <md>]`，内部按三层分模块，输出 Markdown 报告。
- 用途和用法写进 `docs/development/data-quality-audit.md`，并在 `AGENTS.md` 加一行指向它。

## 第一层：取数是否完整

口径按频率区分。应取范围是被审运行的冻结模型目录与 120 日窗口。以下两种结果**分开报告**：目录登记的全部指标、仅模型用到的指标。

- **日频**：在各自市场日历的每个交易日上，每个指标×成员都应有观测。
  - 国内用上交所日历，取运行库中存储的 `trade_cal` 原件。
  - 期货交易所用 `fut_trade_cal` 原件。
  - 美国市场的处理由实施者选定，须在文档中写明，例如脚本内置当年交易所假日表。
  - 日历本身覆盖不到的日子列为"日历未覆盖"，不算缺口。
  - 上游当天确实没出数的，单列为"上游未发布"，与"未取到"分开。依据是回执里该日来源记录为 0，或来源接口明确返回空。
- **月频、季频（含周频）**：
  1. 到判定截止时点为止，该有的最新一期在不在。
  2. 每一期从官方发布（发布日程，或声明的公开可用时间）到入库（系统可用时间）的延迟。超过 1 个交易日宽限的，列出。
- **汇总（派生）数据**：
  1. 存在性：原料齐全的日子，派生值都应存在。
  2. 独立重算：按模型冻结的公式定义，用另写的实现从原料重算，与库中派生值比对；差异超过数值容差的列出。

## 第二层：模型输入是否完整

- 沿用值（落后 1 期）**算完整**。
- 列出模型输入缺失的"指标 × 期次 × 成员"，每项附原因：缺口类别或取数失败原因。
- 分别给出四个分母：最终计划行、冻结输入编号、确认度成员、批次时效（盘点表明这四者口径不同）。
- 核心输入编号追不到原始声明的（留存例外），单列为"追溯断链"，不算缺失。

## 第三层：模型输出是否正确

- **SQL 复查内部一致性**：
  - 核心状态到正式阶段的映射；
  - 确认度计数与成员读法汇总；
  - 报告结构化结论与投影是否一致。
- **独立重算三核心**：根据 ADR、规格与 `CONTEXT.md` 写明的规则（不读也不调用生产实现的计算代码），从冻结的核心输入重算债、股、商品的趋势状态，以及由它们决定的正式阶段，与系统输出逐项比对。规则在文档中有歧义的地方，要记录下来，不得猜测。
- 某个值可疑时，按约定的数据源头核对：一次性、串行调用外部接口，结果记入报告。脚本本身不做外部调用。

## 不做

- 跨日稳定性比对；
- 数值合理性检查（异常跳变、单位倍数）；
- 17 项确认度的独立重算；
- 把检查接进每次运行、阻断门槛；
- 改生产代码（`src/`）。

## 报告

`.scratch/data-quality-audit-20261010/report.md`，按三层分节。每节先给结论，再列明细表。每个问题标注"待开票"或"已知（某票）"。lookback/30 的影响要能单独识别。
