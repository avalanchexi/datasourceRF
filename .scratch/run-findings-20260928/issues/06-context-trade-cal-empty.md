## 分流结论（2026-09-29）

> *This was generated by AI during triage.*

**原现象是读错了数字，不是 TuShare 日历不可靠。** context 口径的 `trade_cal` 由市场广度发起（`breadth.py:300` 的 `breadth_scalars`，`is_open=1`，回看 600 天），与 `stock_basic` 等同组请求共用一份归一化结果（`tushare_context.py:286`），所以回执上的 `row_count` 数的是**整组产出的广度标量**，不是日历行数。逐份核对运行库原件：

| 回执（validated_at） | 原始日历条数 | `row_count` | 含义 |
|---|---|---|---|
| 2026-09-25 16:44 | 403 个开市日 | 1560 | 13 个广度标量 × 120 天（首次补齐窗口） |
| 2026-09-28 04:40–05:02 | 403 | 0 | 窗口内每天都已持有，无新日可算 |
| 2026-09-28 14:11 | 404 | 13 | 只新算 9/28 一天 × 13 个标量 |

广度计算拿到的日历每次都是完整的，广度指标没有受影响。

**顺带查出的真实缺陷：两处按 `api_name='trade_cal'` 取日历、却不分口径，会把 context 回执的归一化内容（广度标量或 `[]`）当成交易日列表。**

- `freshness.launch_calendar`（提交时定目标日）：同一个上海日内已有一次以当天为目标日的运行后再提交，会先读到这份 context 回执——内容是广度标量时提交报错 `fromisoformat: argument must be str`；是 `[]` 时退回"工作日即交易日"，节假日被当成交易日（用例里中秋 9/25 被定为目标日）。
- `czce_warrants.window_trading_days`（郑商所仓单取数的 120 日窗口）：`[]` 的 context 回执被当成"2025-02 至目标日已覆盖"，核心日历有断档时会把断档当成无交易日，拼出一个缺了几个月的"完整"窗口。现库里核心日历覆盖了窗口，对 9/24、9/28 两个目标日修复前后窗口逐日相同，未造成实际影响。

修法：两处都只读核心口径（`parser_version='tushare-core-parser-v0002'`），与 `full_run_requirements.py:57` 一致。回归用例：`test_freshness_contract.py::test_run_submit_ignores_the_breadth_calendar_request_of_a_run_that_day`（两种 context 内容）、`test_czce_warrant_refresh.py::test_the_breadth_calendar_request_does_not_cover_a_gap_in_the_calendar_responses`，修复前均失败。

**本票不做、留作观察的两点**（Codex 复核提出，现在都没有造成实际错误）：

- context 回执的 `row_count` 数的是产出标量，不是原始行数，正是它造成了本票的误读。若以后还要按回执判断取数是否正常，再考虑把两者分开记录。
