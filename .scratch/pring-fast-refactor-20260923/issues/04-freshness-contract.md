# 确定按频率的时效判定契约

## Question

以盘点结果为依据，确定每类频率（日/周/月/季/事件）判定 current、awaiting_release、stale 的具体规则；注册表中每个来源需登记哪些字段（频率、发布滞后、宽限、日频更新时点）；公开可用时间如何由该约定推定（替代 ADR-0017/0018 的逐值证据）；时效失败时是阻断、缺口还是沿用上一期。

## Answer

2026-09-23 与用户逐条访谈确定。

1. **判定时点与目标交易日**：系统平时不常驻，收盘后由人工启动。判定时点 = 本次运行取数结束时冻结的时刻（沿用 `run_cutoff_freeze`），记入加工批次。目标交易日由启动时点自动决定：启动前三核心登记的更新时点已过的最近交易日（例：周一 16:00 启动 → 上周五；周二 10:00 → 周一）。漏跑交易日是否补跑留给票 07。
2. **应有期模型**（取代 `evidence_max_age_days` 固定天数判定，泛化现有 `assess_release_state`）：应有期 = 推算发布时点加宽限已过的最新一期。持有应有期或更新的一期 → current；已过推算发布时点、仍在宽限内、未取到 → awaiting_release；宽限已过仍未取到 → stale。`source_failed`、`permission_denied` 等仍是独立的获取状态。
3. **推算发布时点**：有官方发布预告的用预告日期，预告来源优先级为 TuShare `cn_schedule` → 官方日程页面 → WebSearch（WebSearch 取来的预告如何验证归票 05）；都取不到时按统计期末后第 N 个交易日。时刻用登记的更新时点。
4. **工作日**：一律按上交所交易日历（`trade_cal`）计数，境外来源也一样。
5. **宽限**：日频 1 个交易日；周、月、季频 7 个交易日（用户：月度指标发布日不确定但一般不会不发，一周左右）；可按来源单独覆盖。
6. **事件类**（降准）：不判 stale，有最近一次事件记录即 current，从未取得才记缺口。OMO 公告每个交易日都发，按日频判定，利率值按“有效至变更”展示。
7. **注册表字段**（每个“指标 × 注册来源”一行，代码常量表，随代码版本变化）：频率、发布滞后（交易日数；日频填 0 或 1）、更新时点（上海时间）、宽限（交易日）、依据（文档或日程链接）。派生指标不单独登记，取其输入中最差的时效状态。未登记的来源判为“未配置时效”，按缺口处理（P0 阻断，P1、P2 显示缺口）。顺带修正：两项 PMI 差值的频率由 daily 改为 monthly。
8. **公开可用时间** = min(推算发布时点, 系统首次取得时间)。取代 ADR-0017/0018 的逐值证据。已接受的风险：官方实际发布晚于推算时点时，会有轻微前视（那一期当时会被判为 stale）。
9. **时效失败的处置**：P0 三核心不是目标交易日的值即阻断正式阶段。P1、P2 awaiting_release 时沿用上一期，不算缺口。P1、P2 stale 时，落后应有期 1 期则沿用上一期并标注时效缺口，落后 2 期及以上视为缺失、不参与计算（日频即连续两天取不到）。
10. **生效层**：时效结果只作为加工批次的记录项，不拒收数据，由投影层按第 9 条处置；能拒收数据的只有门③（结构或接口校验）。
