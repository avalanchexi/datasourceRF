# 确定明细留存、汇总保存与加工批次结构

## Question

在现有存储结构上，明细（来源声明、原件）与汇总（派生观测、投影集、阶段史、报告快照）的边界具体落到哪些表/制品；明细留存期如何按公式回看自动推导；过期删除的时机与方式（运行末尾、独立维护命令、物理删除原件）；加工批次的字段、与明细和汇总的关联方式；与 ADR-0006 不可变数据版本、ADR-0012 版本回放冲突部分如何取代。

## Answer

2026-09-23 与用户两轮访谈确定。取代起始决策 5 的“明细＝窗口＋回看、汇总长期保存”。

1. **边界**：明细 = 来源声明、获取回执（`source_claim`、`source_claim_acquisition`、`acquisition_request`）、检索记录（`retrieval_*`）及 `data/artifacts/sha256/` 原件；汇总 = 派生观测、投影集（`projection_set`、`current_projection`）、阶段史、报告快照、缺口提示。
2. **留存期（统一）**：明细、汇总、加工批次**都只留 120 个交易日**（上交所交易日），以最近一次成功运行的目标交易日为终点。不按指标推导、不加回看。
3. **公式回看**：120 日已是最大回看边界；公式确需超出窗口的数据（如三核心趋势的 `window_days + slope_days`、月频同比所需 13 个月）时，运行中从注册来源**临时拉取、只用于计算、不入库**，批次内只记调用参数与原始响应哈希。
4. **删除**：每次手动完整运行**成功发布后**，在运行末尾物理删除超出留存期的明细、汇总、批次记录及无引用原件；失败运行不删。另保留独立维护命令供手动执行。
5. **加工批次落点**：不新建批次表。批次 id = 运行 id，扩展 `parent_run` 登记目标交易日、代码版本等；每次接口调用复用 `acquisition_request`，补齐接口与参数、返回条数、原始响应哈希、时效与结构校验结果。明细经获取回执指向批次；汇总表各加 `batch_id` 列，用**普通文本而非外键**，避免删除时的级联约束。批次记录仅供排查，不展示。
6. **修订与重跑**：与日常获取完全同一路径，不设特殊处理。来源修订值作为新批次的新明细追加，计算取最新一条；同一目标交易日重跑生成新批次与新汇总，当前投影指向最新一次；已生成的汇总不重算。
7. **取代**：取消 `public_as_of` / `system_as_of` 双时点，只保留票 04 的公开可用时间；取消 ADR-0006 的“永久追加、不可变 vintage”与报告 30 天条款；ADR-0012 的版本回放已由起始决策取消。由票 09 统一撰写取代性 ADR。

已知后果（用户已接受）：超过 120 个交易日的阶段史、报告与投影不再可见；明细删除后汇总无法追溯到原值——两者同期删除，故不产生悬空。
