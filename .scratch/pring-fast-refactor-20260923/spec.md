# 精简门禁：快速、可追溯地产出全部硬输出（实施规格）

## Problem Statement

用户想要的是：收盘后手动启动一次完整运行，就能对**最近交易日**拿到全部硬输出——三核心状态、正式阶段、阶段特征卡、宏观/库存状态、120 日证据窗口明细和报告，并且每个值都能追到是哪次加工、从哪个接口取来的。

现状做不到这一点，也改不动：

- 正式输出被一条与主链分开的旁路链卡住：来源认证包 → 候选准入 → 校准/120 日回放 → 激活验收 → 系统验收/演练 → 切换。TuShare 和已注册的官方直连源，也要逐值提供发布证据才算“公开可用”，而多数历史值拿不到这种证据，于是窗口永远不完整。
- 时效按固定天数判定（日 10 / 月 95 / 季 190），和各来源的真实发布节奏对不上；TuShare 某个非 P2 指标解析出错，会让整次运行变成 action_required。
- 数据永久追加、双 as-of、版本回放，库和原件越积越多，追溯靠认证记录而不是加工批次。
- 开发周期被验证拖垮：默认全套约 1848 项、约 8865 秒，93% 耗时来自认证→准入→回放→激活的隔离生命周期夹具（冷建 1742–2068 秒），改一行源码就要重建；还有收据绑定和两轴审查。

## Solution

用户只做一件事：收盘后运行公开的手动完整运行命令。系统自动选定目标交易日，按固定流程走完：

获取 → ③结构/接口校验 → ②时效 → ①120 日明细完整性 → 对缺失与 stale 检索补缺 → 重评①② → 计算 → 原子发布 → 报告 → 清理超出留存期的数据。

- 门禁只剩三道：①120 交易日窗口内应有的明细是否完整；②时效是否正确（按注册的更新频率推定）；③加工是否走了正确接口并通过结构校验。只有③能拒收数据。
- 注册来源（TuShare、已注册官方直连）不再要求认证包和逐值发布证据；公开可用时间 = min(推算发布时点, 系统首次取得时间)。
- WebSearch 结果只从注册白名单主机取值：P0/P1 由登记的解析器解析重新抓取的原文，P2 可接受搜索/AI 抽出的值。
- 三核心补缺失败但只落后 1 期时“核心沿用”，照常产出正式阶段并醒目标注；落后 ≥2 期或冲突才阻断正式阶段，其余输出照常发布。P1/P2 缺失只作为可见缺口，不阻断。
- 一次手动完整运行 = 一个加工批次；明细、汇总、批次统一只留 120 个交易日，运行成功后在末尾物理删除超出部分。
- 模型版本 = 版本号 + 生效指针，用 `model-activate <版本号>` 显式切换，没有验收和回放。
- 开发时只跑受影响的测试（≤3 分钟）；切片收尾跑两例快速冒烟；全套只在真实运行前跑一次。

## User Stories

### 运行与目标交易日

1. 作为运行者，我想在收盘后手动启动一次完整运行，不必指定日期，这样日常操作只有一步。
2. 作为运行者，我想让系统按启动时点自动确定目标交易日（三核心登记的更新时点已过的最近一个上交所交易日），这样周一 16:00 启动算上周五、周二 10:00 启动算周一。
3. 作为运行者，我想对同一个目标交易日重复提交时得到幂等结果，不会并发跑出两套投影，这样误触不会造成混乱。
4. 作为运行者，我想在运行中取消，并保留租约语义，这样不会有两个 Worker 同时写库。
5. 作为运行者，我想让中断的运行直接判为失败，重启时作为新批次从头运行，这样不用理解检查点恢复。
6. 作为运行者，我想让一次运行在三核心阻断时也完整结束并发布宏观、库存、缺口和报告，这样一个核心数据问题不会让我什么都看不到。

### 门③：结构/接口校验

7. 作为运行者，我想让每条取回的数据都经过廉价的结构校验（字段、单位、统计期、非空），不通过就拒收、不入库，这样坏数据进不了计算。
8. 作为运行者，我想让 TuShare 的 P1/P2 解析异常变成拒收加可见缺口，而不是让整次运行 action_required，这样单个指标出错不会拖垮整次运行。
9. 作为排查者，我想在批次记录里看到每次接口调用的接口名、参数、返回条数、原始响应哈希和结构校验结果，这样能定位是哪次调用出的错。

### 门②：时效

10. 作为运行者，我想按“应有期”判定时效：已持有应有期或更新的一期为 current，已过推算发布时点但仍在宽限内为 awaiting_release，宽限已过仍未取到为 stale，这样判定与来源真实节奏一致。
11. 作为运行者，我想让推算发布时点优先采用发布预告（TuShare `cn_schedule` → 官方日程页 → WebSearch），取不到时按统计期末后第 N 个交易日推算，这样月度宏观指标不会因为固定天数阈值被误判。
12. 作为运行者，我想让所有工作日计数都用上交所交易日历，包括境外来源，这样规则只有一套。
13. 作为维护者，我想在代码常量表里按“指标 × 注册来源”登记频率、发布滞后、更新时点（上海时间）、宽限和依据链接，这样时效规则随代码版本一起变化、可审查。
14. 作为维护者，我想让默认宽限为日频 1 个交易日、周/月/季频 7 个交易日，并允许按来源覆盖，这样少数特殊来源不用改全局规则。

## Implementation Decisions

**流程与三道门（Worker 编排）**

- 手动完整运行的主链保持“获取 → 校验 → 派生 → 投影 → 报告”，门的位置固定为：获取 → ③ → ② → ① → 检索补缺（missing、stale）→ 重评 ①② 并冻结输入 → 计算 → 原子发布 → 报告 → 清理。
- 判定时点 = 取数结束时冻结的运行截止时点（沿用现有 `run_cutoff_freeze`），记入批次。
- 只有门③拒收数据；门②只产生记录项，由投影层按“沿用 / 缺口 / 缺失”处置；门①产生缺口清单。
- TuShare 非 P2 解析异常不再抛出中断：Worker 中把整次运行置为 action_required 的分支，改为按③拒收、记缺口、进入检索补缺。
- 取消检查点恢复；保留租约、取消和同目标日幂等。

**时效模块（新写，泛化现有 release-state 判定）**

- 新增“应有期”判定，取代 `evidence_max_age_days` 的固定天数判定，并把现在只实现了 LPR 的发布窗口判定推广到所有来源。
- 时效登记表是代码常量，每行对应“指标 × 注册来源”，字段为：频率、发布滞后（交易日数）、更新时点（上海时间）、宽限（交易日）、依据。派生指标不登记。
- 推算发布时点：先看发布预告（`cn_schedule` → 官方日程页解析器 → WebSearch 取得的白名单日程页），没有预告时用“统计期末后第 N 个交易日 + 更新时点”。
- 公开可用时间 = min(推算发布时点, 首次取得时间)，取代双 as-of 和逐值发布证据。已接受的风险：官方实际发布晚于推算时点时会有轻微前视。
- 目标交易日由启动时点和三核心登记的更新时点共同决定。

**检索验证（改写检索模块）**

- 白名单沿用代码常量，按解析器家族登记“主机 + 路径前缀”，指标经所属家族对应到白名单；P2 宽松路径的主机同样要登记。
- P0/P1：严格路径（重新抓取原文 + 登记解析器），没有解析器的主机不可用；与搜索渠道报的值比较，只查数量级/小数位和时效，不设按指标的数值容差。
- P2：宽松路径，放开 AI WebSearch（去掉现有“P2 禁用 AI WebSearch”的限制）。
- Exa 只在 Tavily 月度限额耗尽后才使用；预算：Tavily 每次运行 16、Exa 8，取消每日上限；AI WebSearch 每个缺口每次运行至多一次。
- 检索验证记录去掉回放/认证相关列（`run_attempt`、`public_complete`、`public_selected_*` 等），改为挂批次 id。
- 新写解析器：中证指数官网（000985、000012）、南华官网（NHII），以及官方发布日程页的解析器。

**存储、批次与留存（schema 迁移）**

- 不新建批次表：批次 id = 运行 id，扩展 `parent_run`，增加目标交易日、代码版本、模型版本号；每次接口调用复用 `acquisition_request`，补齐接口与参数、返回条数、原始响应哈希、时效结果和结构校验结果。
- 明细 = `source_claim`、`source_claim_acquisition`、`acquisition_request`、`retrieval_*` 及内容寻址原件；汇总 = 派生观测、`projection_set`、`current_projection`、阶段史、报告快照、缺口提示。汇总各表增加文本型 `batch_id`（非外键）。
- 留存：三类数据统一保留 120 个上交所交易日，以最近一次成功运行的目标交易日为终点。成功发布后在运行末尾物理删除超出部分及无引用原件；另提供一个独立维护命令，执行同样的清理。现有长历史数据由首次成功运行末尾的清理一次性处理，不另写迁移脚本。
- 旧的认证、准入、回放、激活验收相关表，在删除其所属模块的同一切片内用 schema 迁移删除（ADR-0021/0022 已放弃其语义，不保留数据）。
- 公式回看：超出窗口的数据在运行中临时拉取，只在内存中参与计算，批次记录调用参数和响应哈希。
- 修订和重跑追加新批次，按“取最新”选值；当前投影指向最新一次成功的批次。

**三核心处置（投影层）**

- 补全失败且只落后 1 期时“核心沿用”：用上一交易日的值计算，输出正式阶段并带醒目标注；沿用值不写成明细。
- 落后 ≥2 期或冲突时阻断正式阶段（核心数据待处理），其余输出和报告照常发布。
- P1/P2：awaiting_release 时沿用，不算缺口；stale 落后 1 期时沿用并记时效缺口；落后 ≥2 期视为缺失，不参与计算。

**首次初始化与漏跑补算（共用逐日计算）**

- 库中没有汇总时进入首次初始化：取 120 交易日明细和公式回看，逐日计算并重建阶段史，只为目标交易日生成报告。
- 日常运行先检测窗口内漏跑的交易日，用同一套逐日计算补算，每一日只用公开可用时间不晚于该日的明细，补算日不生成报告。

**模型版本**

- 删除候选、准入、回放和激活验收；`model-activate <版本号>` 只移动生效指针。运行读取生效指针，把版本号记入批次；切换不重算已有汇总。

**模块与命令去留**

- 整删：预检完整性、模型评估、验收、切换模块。
- 迁出后删除：候选准入模块（目录迁移定义和结构校验迁到目录模块）、来源认证模块、演练模块（smoke 命令一并删除）。
- 逐处剥离：来源契约审查、证据、检索证据、完整运行要求模块中的认证门和逐值发布证据。
- CLI 删除 model-source-certify、model-input-preflight*、model-accept / model-replay、验收、演练、切换相关命令；保留 run-submit、Worker、model-activate，新增留存清理维护命令。
- 生效目录保持 59 项（P0 6 / P1 41 / P2 12，CNY030 为 P2），组装结果不变。
- 目录修正：两项 PMI 差值的频率改为 monthly；沪深融资新 ID 接入 TuShare `margin`；P2 的 USDCNY 16:30、VIX、SOX 登记白名单主机，走宽松检索路径。

**开发验证工具**

- `check.py`：去掉 `--freeze` 和收据语义，`HEAVY_FILES` 只保留改写后的完整目录用例；删除输入收据工具中的收据用途及其维护测试。
- 不引入 pytest-xdist。

**建议的纵向切片顺序**（拆票时参考，不作硬约束）

1. 批次与时效骨架：扩展 `parent_run` 和 `acquisition_request`，加入时效登记表和应有期判定，接入 Worker 并写入批次；三道门先以“只记录”方式并行存在。
2. 去认证主链：剥离主链模块中的认证标签和逐值发布证据，把公开可用时间改为 min 规则，取消双 as-of，并改写两例快速冒烟。
3. 删除旁路链：迁出目录迁移和结构校验，整删 4+3 个模块及其 CLI、专属测试和相关表；简化 `model-activate`。
4. 门③改拒收，TuShare 解析异常改为缺口。
5. 门①缺口清单与页面/报告呈现，包括“检索未通过”分组。
6. 检索补缺按新规则改写：白名单、严格/宽松路径、预算、Exa 备用、放开 AI WebSearch。
7. 三核心：官方页面解析器、补全链、核心沿用与 ≥2 期阻断，并补反例测试。
8. 留存清理：运行末尾清理和独立维护命令；公式回看改为临时拉取。
9. 首次初始化与漏跑补算。
10. 取数补洞：`margin` 新 ID、`cn_schedule` 与日程页、PMI 频率、P2 白名单、核实 `index_dailybasic`。
11. 验证工具收尾：`check.py`、收据清理、`HEAVY_FILES`；随后全套跑一次，再做真实运行。

## Testing Decisions

- **唯一测试接缝（用户已确认）**：手动完整运行的公开入口。测试通过 run-submit 提交，让 Worker 执行，再读取公开输出（页面/投影、报告、缺口清单）和批次/检索记录来断言。TuShare、官方直连、Tavily/Exa/AI 搜索的 HTTP 和时钟都用替身，保持离线。三道门、时效判定、检索验证、核心沿用/阻断、留存清理、首次初始化、漏跑补算和 `model-activate` 都经这一入口测试，不给内部函数单独开接缝。
- 唯一例外是 `check.py` 工具本身（quick/full、去掉 `--freeze`、`HEAVY_FILES`），在工具入口测试。
- 好测试的标准：只断言外部可见的行为，即正式阶段是否产出、有没有“核心沿用”标注、缺口清单的分类和原因、批次里登记的接口/哈希/时效结果、清理后哪些数据还在；不断言内部函数调用顺序或中间结构。时效边界（日/周/月/季/事件；awaiting_release 与 stale 的交界；P1 落后 1 期与 2 期）用时钟替身和登记表参数化，同样经这一入口。
- 需要覆盖的场景：
  - 正例：注册来源全部 current → 全部硬输出，批次完整。
  - 三核心落后 1 期 → 核心沿用；落后 ≥2 期 → 正式阶段阻断，其余输出照常。
  - TuShare P1 解析异常 → 拒收、记缺口、经检索补缺成功或失败。
  - P0/P1 搜索值数量级不一致 → 不采纳，出现在“检索未通过”中。
  - P2 宽松路径被采纳。
  - Tavily 达到月度限额 → 改用 Exa。
  - 未配置时效 → 按优先级处置。
  - 成功运行清理超窗数据；失败运行不清理。
  - 首次初始化生成窗口内逐日汇总，只出一份报告。
  - 漏跑补算不使用晚于补算日公开的明细。
  - `model-activate` 切换版本后，新运行记录新版本号，旧汇总不变。
- 可沿用的已有测试：
  - 快速正例：`test_core_history_refresh::test_manual_run_cannot_backdate_daily_core_availability`（补报告断言）、`test_worker_execution::test_worker_completes_a_valid_noncanonical_projection_and_report`（去掉 `certification_status`）。
  - 完整目录正例：`test_worker_registered_catalog` 中的官方 PPI 回退例，夹具改为“直接登记 + 显式切换”的简单模型。
  - 三核心反例：以 `test_integrated_worker_core_gap` 为底，按新规则改写并新增“核心沿用”一例。
- 执行策略按 ADR-0025：日常用 `check.py quick` 选受影响的测试（≤3 分钟）；切片收尾跑两例快速正例（≤1 分钟）；涉及 Worker 编排、目录或来源时加跑完整目录正例和反例；全套在真实运行前跑一次并如实记录耗时（推断 30–50 分钟）。
- 被删门禁的测试随模块在同一切片删除或改写；不保留依赖隔离生命周期夹具的测试。

## Out of Scope

- 不改三核心、趋势/阶段公式、持续性规则和指标目录成员（CNY030 已是 P2）。
- 不做六年/三年长历史抢救和离线校准；超过 120 个交易日的阶段史、报告和投影不再可见（用户已接受）。
- 不新增付费数据源、厂商模型 API、多 Worker、双写或数据库备份。
- 不设人工采用检索结果的入口；批次和检索记录不在页面或报告中展示。
- 不引入并行测试；两轴审查不强制。
- 旧 effort（pring-data-acquisition-repair、pring-window-publication-20260922）开放票的关闭或“被取代”标记，另行处理，不属于本规格的实施切片。
